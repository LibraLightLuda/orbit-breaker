## 1. 설계 결론과 현재 프로젝트 기준

**권장 구조는 기존 Godot 게임을 유지하면서, Sites가 웹 배포·게스트 식별·기록 조회를 맡고, 별도의 Godot 전투 서버가 공식 도전과 2인 협동을 판정하는 구성이다.** 랭킹 데이터는 D1, 고스트와 대용량 게임 파일은 R2를 우선 사용한다. Sites에서 검증되지 않는 기능은 정해진 기준에 따라 독립 Cloudflare 서비스로 옮긴다.

기존 혼자하기는 네트워크 없이 동작하는 현재 모드로 보존한다. 온라인 기능을 사용하려고 기존 기록이나 설정을 초기화할 필요가 없어야 한다.

**사용자와 확정한 제품 조건**

| 항목 | 확정 사항 |
|---|---|
| 첫 서비스 | 한국 중심 소규모 공개 베타, 동시 접속 50명 목표 |
| 비용 | 월 인프라 예산 약 10만 원 우선. 실제 전투 수용량을 넘으면 입장 제한 |
| 사용자 식별 | 회원가입 없이 게스트로 온라인 기능에 참여 |
| 공식 순위 | 접속 상태에서 서버가 판정한 공식 도전만 등록 |
| 협동 강화 | 두 플레이어의 전투를 함께 멈추고 선택 |
| 협동 사망 | 동료가 접근해 구조하는 방식 |
| 이번 단계 | 분석과 설계만 수행. 구현·배포·문서 파일 작성은 하지 않음 |

**분석 기준은 현재 작업본인 3.19 / `clarity-20261016`이다.** 공개 v3.19.0은 이전 `audit-20261014` 세대이므로, 공개본을 최신 소스 기준으로 간주하지 않는다. 기존 미커밋 변경도 구현 출발점에 포함하여 보존한다. 게임 규칙과 배포 사실은 각각 [SURVIVAL_V3.md](D:/Antigravity/NewProject/docs/SURVIVAL_V3.md), [VALIDATION_V3.md](D:/Antigravity/NewProject/docs/VALIDATION_V3.md)를 따른다.

프로젝트에서 확인한 온라인 확장의 핵심 조건은 다음과 같다.

- **전투 계산을 재사용할 기반이 있다.** `RunModel`은 `RefCounted`이고, 전투는 `step()`으로 진행된다. 화면·입력과 완전히 분리되지는 않았지만 Godot headless 서버에서 같은 계산을 실행하기에 적합하다. [전투 진행 코드](D:/Antigravity/NewProject/scripts/run_model.gd:389)
- **현재 모델은 플레이어 한 명을 전제로 한다.** 위치·체력·강화·무기·피해·위험층 보상·미션이 단일 플레이어 상태를 참조한다. 협동은 RPC를 추가하는 수준으로 구현할 수 없다.
- **고스트는 시각적 전장 기록이다.** 약 0.2초 간격의 스냅샷, 객체 생성·소멸 기록, 보간과 탐색 기능을 갖췄다. 전투를 다시 계산하는 결정론적 입력 리플레이나 완전한 서버 복구 체크포인트는 아니다. [고스트 캡처](D:/Antigravity/NewProject/scripts/ghost_replay.gd:153)
- **현재 랭킹은 로컬이다.** 이름·난이도별 최고 기록과 상위 10명을 관리한다. 온라인 식별자를 닉네임으로 대체해서는 안 된다.
- 전투·아이템·재해·미션 난수가 분리되어 있다. 단일 플레이어에서 난수 호출 순서를 바꾸지 않는 것이 중요한 회귀 조건이다.
- 웹 내보내기는 단일 스레드이며 기존 모바일 조작·사운드·고정 화면 메뉴를 갖추고 있다. 온라인 도입을 이유로 이를 다시 만들지 않는다.

이번 분석에서 기존 모델 35개, 생존 198개, 전투 확장 194개로 **427개 검사를 실행해 통과**했다. 최대 밀도 성능 검사도 평균 **5.332ms**, p95 **9.542ms**로 통과했다. 이는 현재 Windows PC의 단일 전투 검사이며 Linux 서버 수용량이나 온라인 플레이 품질의 증거는 아니다.

## 2. 기술 구성과 선택 이유

### 권장 구성

| 구성 요소 | 책임 | 선택 |
|---|---|---|
| Godot 웹 클라이언트 | 기존 혼자하기, 화면·입력·사운드, 온라인 전투 표시, 고스트 관전·경쟁 | 현재 Godot 4.7.1과 콘텐츠 유지 |
| Sites 웹 서비스 | 게임 진입점, 게스트 세션, 온라인 API, 랭킹·개인 기록, 고스트 접근 권한 | 지원되는 Sites 서버 스타터와 배포 흐름 사용 |
| D1 | 게스트 프로필, 시즌, 경기 결과, 개인 최고 기록, 고스트 메타데이터 | 구조화된 소규모 서비스 데이터에 사용 |
| R2 | 대용량 게임 파일, 고스트 청크와 완료 매니페스트 | 데이터베이스에 리플레이 본문을 넣지 않음 |
| 전투 서버 | 공식 솔로·2인 협동의 전투, 난수, 선택지, 피해·보상·결과 판정 | Linux Godot headless |
| 방 관리 서비스 | 입장권 검증, 방·정원·대기열, Godot 프로세스 관리, 결과 재전송 | 작은 Node.js 서비스 |
| HTTPS/WSS 진입점 | TLS, 연결 제한, 전투 서버 연결 | Caddy와 단일 서버로 시작 |

초기에는 **전투 한 판당 Godot 프로세스 하나**를 사용한다. 솔로와 협동 모두 같은 서버 실행물을 사용하고 참가자 수만 다르게 한다. 프로세스 간 장애 격리와 자원 측정이 쉽고, 저예산 입장 제한과도 잘 맞는다. 프로세스 풀이 필요하다는 측정 결과가 나오기 전에는 별도 분산 스케줄러를 만들지 않는다.

### 주요 선택지 비교

| 결정 | 채택 이유 | 이번에 채택하지 않는 방식 |
|---|---|---|
| 서버 권위형 전투 | 공식 점수와 협동 판정의 신뢰 근거가 같아지고 기존 GDScript를 재사용할 수 있음 | 브라우저 점수 직접 제출, 방장 클라이언트 판정 |
| 기존 Godot 서버 실행 | 게임 규칙을 다른 언어로 이중 구현하지 않아도 됨 | 전투 전체를 Sites의 TypeScript로 재작성 |
| 상태 스냅샷 기반 고스트 | 현재 관전 기능과 호환되고 플랫폼 간 재현 오차를 피함 | 입력·시드만으로 모든 브라우저에서 동일한 전투를 재현한다고 가정 |
| D1 + R2 | 기록과 대용량 파일의 성격을 분리하고 운영 구성요소를 줄임 | 처음부터 PostgreSQL·Redis·별도 메시지 브로커 추가 |
| WSS 우선 검증 | 브라우저 호환성과 운영이 단순함 | 검증 없이 WebRTC·TURN부터 도입 |
| 게스트 식별 + 복구 코드 | 가입 없이 시작하면서 기기 변경 시 기록을 찾을 수 있음 | 닉네임만으로 소유권 확인 |
| 방 코드 중심 협동 | 2인 친구 초대라는 핵심 흐름을 작게 완성할 수 있음 | 초기부터 자동 매칭·친구 그래프·채팅 운영 |

**WSS는 선행 검증을 통과해야 확정한다.** Godot 공식 문서도 TCP 기반 WebSocket의 지연 특성이 빠른 실시간 게임에 불리하다고 설명한다. 이동 예측과 작은 상태 패킷을 적용해도 기준을 만족하지 못하면, 서버 권위를 유지한 채 전투 전송만 WebRTC DataChannel로 전환한다. 이때 Linux 서버의 네이티브 확장 호환성과 TURN 비용까지 다시 검증한다. [Godot WebSocket 문서](https://docs.godotengine.org/en/stable/tutorials/networking/websocket.html), [Godot WebRTC 문서](https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html)

### Sites에서 확인된 사실과 검증이 필요한 부분

공식 문서는 Sites의 HTTP·HTTPS·WebSocket, D1 및 R2 지원을 명시한다. 설치된 Sites 지침은 서버 런타임이 Cloudflare Workers임을 설명한다. **이 사실만으로 네이티브 Godot 프로세스나 지속적인 60Hz 게임 서버를 Sites 안에서 실행할 수 있다고 판단하지 않는다.** [Sites 공식 문서](https://learn.chatgpt.com/docs/sites?surface=web), [데이터와 연결](https://learn.chatgpt.com/docs/sites/data-and-connections)

현재 환경에서는 Sites 연결 도구를 호출할 수 있었고, 소유한 Site 목록은 비어 있었다. 따라서 배포·저장·외부 WSS 연결은 아직 실증하지 않았다.

특히 현재 게임 파일은 다음 크기다.

- WebAssembly: **39,513,091바이트**
- PCK: **19,395,368바이트**

Cloudflare Workers 일반 정적 파일 한도는 파일당 25MiB이므로, Sites에 현재 산출물을 그대로 넣어 성공한다고 가정하면 안 된다. Sites가 다른 전달 경로를 제공하는지는 별도 확인한다. [Cloudflare 제한 문서](https://developers.cloudflare.com/workers/platform/limits/)

첫 구현 검증에서 다음 순서로 배포 방식을 확정한다.

1. Sites에서 현재 게임 파일의 배포·다운로드·실행 가능 여부를 확인한다.
2. 큰 파일에 제한이 있으면 **R2 객체를 같은 사이트 경로에서 스트리밍**한다. MIME, Content-Length, 압축 헤더, 캐시, SHA-256을 검증한다. Worker 메모리에 전체 WASM을 읽어 들이지 않는다.
3. 대용량 전달·필수 보안 설정·백업 복구 중 하나라도 Sites에서 충족되지 않으면, 동일한 웹/API 코드를 **직접 관리하는 Cloudflare Workers + D1 + R2**로 배포한다.
4. Sites는 이 경우 게임 소개와 실제 플레이 주소 안내에 사용한다. 게임은 안정적인 하나의 출처에서 최상위 페이지로 실행한다.

이 대안은 게임이나 데이터 모델을 다시 만드는 전환이 되어서는 안 된다. 단일 스레드 웹 내보내기를 유지하며, iframe을 기본 실행 방식으로 삼지 않는다. Godot 웹 문서에 명시된 저장소·백그라운드 탭·오디오 제약도 실제 브라우저 검증에 포함한다. [Godot 웹 내보내기 문서](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

## 3. 구현할 동작과 반드시 유지할 계약

### 전투 모델과 클라이언트 분리

전투 상태를 다음 두 범주로 분리한다.

- **전장 공통 상태:** 시간, 적, 위험 구역, 공통 드롭, 재해, 보스, 전장 난수, 팀 결과.
- **플레이어 상태:** 위치·방향, 체력, 돌진, 무기·강화·진화·분기, 버프, 개인 미션 진행, 개인 전투 통계.

모든 공격·설치물·피해·획득 이벤트에는 필요한 `owner_player_id` 또는 대상 식별자를 둔다. 현재 `friendly`만으로 표현하는 탄환 구분은 소유자 정보와 함께 사용한다.

구현 원칙은 다음과 같다.

- 기존 단일 플레이어 `RunModel` 진입점과 저장 호환성을 유지한다.
- 공유 전장은 한 틱에 한 번만 진행한다. 플레이어별로 기존 `RunModel.step()`을 두 번 호출해 적·시간·드롭을 중복 진행시키지 않는다.
- 1인 구성에서 기존 난수 호출 순서·보상·타이밍이 유지되는지 고정 입력 회귀로 확인한다.
- 클라이언트는 온라인 전투에서 피해·점수·아이템 획득을 확정하지 않는다.
- 로컬 플레이어의 이동·돌진은 즉시 예측해서 표시하고 서버 상태로 보정한다. 피해·사망·보상은 서버 확인 후 표시한다.
- 서버는 음원을 재생하지 않는다. 위치와 소유자가 붙은 의미 이벤트를 보내고 기존 사운드·효과를 클라이언트가 재생한다. 예측과 서버 확인으로 같은 효과음이 두 번 나지 않도록 이벤트를 식별한다.
- 고스트의 화면 복원 함수를 서버 재접속 복구나 전투 재개에 사용하지 않는다.

### 네트워크와 방의 수명

초기 설정은 서버 **60Hz 고정 시뮬레이션**, 입력 전송 최대 **60Hz**, 상태 전달 **20Hz**다. 원격 객체는 약 100ms 보간 버퍼를 사용하며, 본인 이동은 예측 표시한다. 네트워크 상태에 따라 상태 전달 빈도는 낮출 수 있지만 전투 시간과 판정 주기는 바꾸지 않는다.

프로토콜은 다음을 구분한다.

| 메시지 종류 | 최소 내용 |
|---|---|
| 연결·입장 | 프로토콜 버전, 지원 빌드·규칙 버전, 일회용 입장권 |
| 플레이어 입력 | 순번, 이동 벡터, 돌진 방향, 버튼 실행 식별자 |
| 선택 응답 | 서버가 발급한 선택 창 ID와 제시된 선택지 ID |
| 서버 상태 | 서버 틱, 마지막 처리 입력, 플레이어·객체 상태, 생성·제거, 이벤트 |
| 제어 | 준비, 시작, 정지 요청, 재접속, 종료 사유 |
| 결과 | 경기 ID, 검증 상태, 저장 상태, 고스트 상태 |

위치·피해·점수·임의 강화 결과를 클라이언트 입력으로 받지 않는다. 패킷 크기, 빈도, 숫자 범위, 유한값, 벡터 길이, 선택 창 유효성, 중복 실행을 서버에서 검사한다. 역직렬화로 객체나 코드를 생성하는 형식을 사용하지 않는다.

상태 전달은 안정적인 객체 ID와 변경분을 사용한다. 전체 재동기화는 입장·재접속 및 기준 상태 불일치 때 수행한다. 전송 대기량이 커지면 오래된 미전송 시각 상태를 합치고, 제어 메시지를 무한히 밀어내지 않는다.

방 흐름은 **생성 → 참가 → 양쪽 준비 → 서버 시작 → 전투/선택/재접속 → 결과 → 종료**로 고정한다.

- 최대 2명, 초대 링크와 방 코드 지원. 시작 후 새 참가자는 받지 않는다.
- 방장이 전투 권위를 가지지 않는다. 시작 전 방장 이탈은 남은 사람에게 방 관리 권한을 넘긴다.
- 중복 시작, 마지막 자리 동시 참가, 한 게스트의 중복 경기 시작은 원자적으로 차단한다.
- 로비 대기 시간은 10분, 경기의 실제 경과시간 상한은 30분으로 둔다.
- 입력이 끊기면 이동·버튼을 중립화한다. 연결 장애가 확인되면 재접속 정지로 전환한다.
- 재접속 정지는 플레이어당 누적 30초까지 허용한다. 모든 전투 타이머를 함께 멈춘다.
- 기한을 넘기면 경기는 중단 처리한다. 공식 결과로 올리거나 싱글 순위로 바꾸지 않는다.
- 이미 서버에서 완료한 경기는 브라우저 종료와 무관하게 저장하고, 재접속 후 조회할 수 있어야 한다.
- 서버 프로세스가 죽은 진행 중 경기는 중단한다. 초기 버전에서 임의의 중간 상태 복원이나 방장 승계로 계속 진행하지 않는다.

### 2인 협동 규칙

협동은 별도 `coop-v1` 규칙으로 관리한다. 아래 값은 구현·검증 가능한 초기 기준이며, 공개 시즌 시작 전 플레이 검증으로 조정할 수 있다.

| 영역 | 초기 협동 규칙 |
|---|---|
| 기본 전투 | 기존 기체·전장·무기·진화·분기·600초 종료를 유지. 아군 피해와 기체 간 충돌 없음 |
| 적의 목표 | 가장 가까운 생존 플레이어. 공격 예고가 시작되면 발동까지 목표·방향을 고정 |
| 등장 위치 | 두 생존 플레이어 모두에 대해 기존 최소 안전거리 검사 |
| 초기 난도 | 기존 대비 등장 빈도 1.2배, 적 체력 1.6배. 이동·접촉/탄 피해·위험 예고는 유지 |
| 개체 상한 | 기존 상한을 출발점으로 사용. 두 명이라는 이유로 적·탄·효과 상한을 일괄 두 배로 하지 않음 |
| 장비 기반 압박 | 두 참가자의 장착 파츠 수 평균을 사용. 도중 이탈·사망으로 난도가 내려가지 않음 |
| 처치·팀 점수 | 적 사망은 한 번만 처리. 최종 유효 공격 소유자의 위험층·점수 버프를 적용해 팀 점수에 한 번 합산 |
| 경험치 | 경험치 객체는 한 번 회수하고 생존 플레이어 각각에게 기본 경험치를 지급. 각자의 위험층·경험치 버프를 한 번 적용 |
| 아이템 | 먼저 접촉한 플레이어가 획득. 동시 접촉은 거리, 플레이어 ID 순으로 결정 |
| 파츠 | 공용 탐사 파츠는 회수 시 두 참가자에게 지급. 개인 미션 보상 파츠는 소유자에게만 지급 |
| 미션 | 공개·시작·마감 시각과 제시 미션은 공통, 진행·보상은 개인별. 처치형 진행은 해당 적에게 최근 5초 내 유효 피해를 준 참가자에게 인정 |
| 행성 방어 | 생존자 한 명 이상이 원 안에 연속 12초 머물면 성공. 보상은 한 번 발생하고 팀 점수·공유 경험치 규칙 적용 |
| 최종 작전 | 08:50~09:00에 두 참가자가 동의해야 도전. 무응답·불일치는 생존 계속 |
| 돌파·종료 | 팀 단위 보스 격파와 5분 돌파를 판정. 전원 행동 불능 또는 600초에 종료 |

강화·전술 분기는 서버가 선택 창을 열고 전장을 함께 정지한다. 해당 플레이어들만 선택하며, 둘 다 선택할 것이 있으면 동시에 고른다. 강화는 20초, 분기는 15초 뒤 자동 선택한다. 자동 선택은 제시된 회복 선택지가 있으면 그것을, 없으면 첫 선택지를 사용한다. 선택지 생성이나 난수 추첨을 다시 실행하지 않는다.

수동 정지는 상대 동의가 필요하며 한 번 최대 30초, 방 전체 누적 60초로 제한한다. 개인 설정 화면을 열었다는 이유만으로 온라인 전장이 멈추지 않는다.

구조 규칙은 다음과 같다.

- 체력 0이면 15초간 구조 가능한 상태가 된다. 공격·획득·적 목표에서는 제외한다.
- 동료가 64px 안에서 3초간 유지하면 구조한다. 이탈·돌진·전투 피격 시 구조 진행을 초기화한다.
- 최대 체력 30%로 복귀하며 2초의 전투 무적을 준다. 자연 붕괴·외곽 피해는 면제하지 않는다.
- 플레이어당 한 경기 한 번 구조받을 수 있다. 기한 초과 또는 두 번째 사망 후에는 동료를 관전한다.
- 구조할 수 있는 생존자가 없으면 즉시 종료한다.

협동 기록과 보상은 기존 솔로 기록·난이도 해금·업적 통계에 합산하지 않는다. 온라인 개인 기록에서 협동 전적을 별도로 제공한다.

### 게스트 식별과 기록 보존

게스트도 서버가 발급한 임의 `player_id`와 세션을 가진다. 닉네임은 표시용이며 변경하거나 중복될 수 있다.

- 세션은 충분히 긴 무작위 토큰과 `Secure`, `HttpOnly`, 적절한 `SameSite` 쿠키로 관리한다. 서버에는 토큰 원문 대신 해시를 저장한다.
- 최초 온라인 참여 시 복구 코드를 발급한다. 복구 코드 저장은 권장하되 플레이를 막지 않는다.
- 복구 코드로 새 기기에 연결하면 코드를 교체하고 이전 세션을 폐기한다.
- 쿠키와 복구 코드를 모두 잃으면 해당 게스트의 소유권을 되찾을 수 없다는 점을 계정 화면에서 짧게 안내한다.
- 닉네임 정제, 요청 속도 제한, 방 코드 추측 제한, 신고·기록 숨김·세션 차단을 제공한다.
- 게스트 재생성과 자동 플레이를 완전히 막을 수 있다고 주장하지 않는다. 초기 서비스는 현금성 보상이나 1인 1계정 보증을 전제로 하지 않는다.

기존 로컬 저장은 그대로 유지한다. 온라인 기록 캐시는 별도로 관리하며 서버 기록으로 기존 프로필을 덮어쓰지 않는다. 온라인에서는 모든 기체·전장·난이도를 동일 조건으로 선택할 수 있게 해, 변조 가능한 로컬 해금 상태를 경쟁 권한으로 사용하지 않는다.

웹 출처가 바뀌면 기존 브라우저 저장이 자동 이전되지 않는다. 공개 전환 전에 기존 사이트에서 **기록·설정·연결된 고스트를 내보내고 새 사이트에서 가져오는 흐름**을 제공한다. 가져온 기록은 개인 로컬 기록으로 유지하고 공식 순위로 승격하지 않는다.

### 랭킹·시즌·결과 저장

공식 랭킹에는 서버가 완료한 경기만 들어간다. 브라우저는 완료된 경기의 공개 등록·닉네임 표시를 요청할 수 있지만 점수 본문을 확정하지 못한다.

- 기본 순위 구분은 `시즌 × 규칙 버전 × 솔로/협동 × 난이도 × 전장`이다. 기체 필터도 제공한다.
- 솔로는 플레이어별 최고 기록, 협동은 두 플레이어 ID를 정렬한 팀별 최고 기록을 노출한다.
- 정렬은 점수 내림차순, 생존 틱 내림차순이다. 두 값이 같으면 공동 순위로 표시하고 달성 시각·경기 ID로 화면 순서만 안정화한다.
- 개인 기록, 개인 최고, 상위 기록, 내 순위 주변을 제공한다. 전체 데이터를 한 번에 내려받지 않고 커서 페이지를 사용한다.
- 시즌은 한국 시간 기준 월 단위다. 경기가 시작된 시즌에 귀속하며 종료 후 24시간의 저장 유예 뒤 순위를 확정한다.
- 점수에 영향을 주는 규칙 변경은 새 경쟁 구분으로 분리한다. 시각·오디오 수정만으로 시즌을 초기화하지 않는다.
- 이전 시즌 기록은 읽기 전용으로 남긴다. 서로 다른 규칙의 점수를 무조건 합친 누적 순위를 만들지 않는다.

저장 경로는 **서버 결과 생성 → 서버 디스크의 재전송 대기 자료 기록 → 인증된 결과 API → D1 결과·최고 기록 갱신 → 고스트 완료 연결**이다.

경기 ID는 중복 방지 키다. 같은 경기의 재전송은 한 번만 반영하고, 같은 ID에 다른 결과가 오면 거부·기록한다. 고스트 업로드가 늦어져도 검증된 점수는 보존하며 고스트 상태를 `처리 중`으로 표시한다. 업로드 완료 전 고스트를 재생 가능한 상태로 노출하지 않는다.

### 고스트 관전과 경쟁

기존 로컬 고스트 판독기는 유지하고, 온라인 고스트에는 별도의 버전 있는 포맷을 추가한다.

- 서버의 실제 전장을 약 5Hz로 기록하고, 플레이어 이동·돌진 궤적은 20Hz로 보강한다.
- 짧게 생성됐다 사라지는 공격·효과는 생성·소멸 시점에서 기록한다. 정기 스냅샷 사이에 사라졌다는 이유로 누락하지 않는다.
- 적·탄·아이템·위험·미션·보스 보호장치·전술 분기·두 플레이어 소유권을 포함한다.
- 점수·체력·선택 결과는 실제 서버 값을 사용한다. 관전 화면의 프레임 사이 움직임은 보간 표현이며, 원 플레이의 모든 렌더 프레임과 픽셀 단위 일치를 보장하지 않는다.
- 포맷, 규칙·콘텐츠 식별자, 경기 설정, 참가자, 시드, 청크 해시와 완료 상태를 매니페스트에 저장한다.
- 2초 단위 청크를 기준으로 점진 다운로드·탐색한다. 초기 제한은 압축 청크 1MiB, 해제 청크 4MiB, 경기 전체 압축 64MiB다. 초과하면 기록을 조용히 자르지 않고 실패 상태와 원인을 남긴다.
- 기존 파일 판독기의 32MB 제한을 전역으로 해제하지 않는다. 새 형식에 별도의 크기·스키마·객체 수 검사를 적용한다.

관전은 기존 재생·일시정지·배속·탐색을 재사용하고, 협동 기록에는 시점 전환을 추가한다.

고스트 경쟁은 동일 기체·전장·난이도·초기 시드로 시작하는 **연습 도전**이다. 상대 기체는 충돌·보상에 관여하지 않고 같은 전투 시각의 궤적과 점수를 보여준다. 플레이어의 행동과 선택에 따라 이후 전장은 달라질 수 있으므로 완전히 동일한 적 배치를 보장하지 않는다. 이미 알려진 시드를 반복하는 고스트 도전은 일반 공식 순위에 넣지 않는다.

### 공개 인터페이스와 UI

외부 인터페이스는 다음 범위로 고정한다. 내부 파일 배치와 작은 헬퍼 구조는 Sol 6.1이 기존 코드에 맞게 결정한다.

| 인터페이스 | 역할 |
|---|---|
| 게스트 생성·복구·세션 종료 API | 게스트 소유권 관리 |
| 개인 프로필·기록 API | 온라인 전적과 저장 상태 조회 |
| 입장권 API | 짧은 만료시간의 일회용 전투 입장권 발급 |
| 방 제어 프로토콜 | 생성·참가·준비·시작·정지·재접속 |
| 랭킹 API | 시즌·규칙·모드 필터, 상위·주변 순위 |
| 고스트 매니페스트·청크 API | 접근 권한을 확인한 관전 자료 전달 |
| 서버 전용 결과·고스트 업로드 API | 신뢰하는 전투 서버의 결과만 수용 |
| 서비스 설정 API | 호환 빌드, 현재 시즌, 점검·입장 가능 상태 |

기존 Godot 메인 화면에는 `혼자하기`, `온라인 도전`, `2인 협동`, `기록`을 자연스럽게 통합한다. 별도의 웹 관리 화면처럼 보이는 게임 로비를 덧붙이지 않는다.

신규 화면도 기존 색·기체·아이콘·사운드 언어를 사용한다. 핵심 선택·준비·복귀는 세로 스크롤 없이 보여주고 기록 목록은 페이지로 나눈다. 협동 HUD는 동료 선체·구조 상태·화면 밖 방향, 짧은 연결 상태 표시만 추가한다. 입력 초점·선택 상태는 회전과 새로고침에서 가능한 범위로 보존한다.

**P0의 판정 기준**

- 현재 WASM/PCK가 실제 배포 경로에서 온전히 전달되고 메인·전투·오디오·저장이 동작해야 한다.
- 두 클라이언트로 RTT 80ms, 지터 20ms, 손실 1% 조건을 검사한다. 목표는 입력 처리 지연 p95 150ms 이하, 본인 위치 보정 오차 p95 13px 이하·p99 52px 이하이다.
- RTT 200ms·손실 3%에서는 연결 경고·재접속·정상 중단을 검사한다. 이 조건을 쾌적한 플레이 보장으로 홍보하지 않는다.
- WSS가 기준에 실패하면 WebRTC를 검증한다. 두 방식 모두 실패하면 공식 실시간 기능 공개를 막고 원인을 해결한다.
- Linux에서 실제 최대 밀도와 고스트 기록을 포함해 측정한다. 후보 입장 상한에서 CPU 여유 30% 이상, 메모리 70% 이하, 지속적인 틱 밀림 없음이 필요하다.
- 저가 서버의 CPU 사용 제한까지 드러나도록 12시간 부하 검사를 수행한다.
- 데이터 백업을 만드는 데 그치지 않고 빈 검증 환경으로 복원해야 한다.

**필수 회귀·운영 시나리오**

- 3개 기체, 3개 전장, 4개 난이도와 모든 진화·분기·보스 보호장치·최종 작전.
- 같은 적 동시 처치, 같은 아이템 동시 접촉, 두 사람 동시 강화·사망, 구조 중 피격.
- 시드 고정 반복, 음소거·효과 줄이기·관전이 전투 난수를 바꾸지 않는지 확인.
- 잘못된 입장권, 타인 경기 접근, 재사용 입장권, NaN·무한대·초대형 패킷·과도한 입력.
- 방 참가 경쟁, 중복 결과, 저장 API 장애, 고스트 일부 업로드, 데이터베이스와 객체 저장소 상태 불일치.
- 새로고침, 탭 백그라운드, 모바일 회전, 연결 단절, 서버 프로세스 종료, 배포 중 재접속.
- 기존 저장·백업·구형 고스트, 출처 이전, 복구 코드 교체, 로컬 저장 공간 부족.
- 데스크톱 Chrome·Edge·Firefox, Android Chrome와 iOS Safari의 실제 기기 검사. 화면 크기만 바꾼 브라우저 검사는 별도로 표기.
- 기존 동일 장면에서 솔로 성능 p95 10% 이내 회귀 기준. 자동 검사와 별개로 두 사람이 타격감·선택 대기·구조·협동 난도를 평가.

## 5. 운영·배포·문서 인계 기준

**비용과 수용량**

50명은 설계 목표이며 초기 입장 보장 수치가 아니다. 현재 스트레스 평균 5.332ms를 단순 환산하면 60Hz 솔로 50판은 초당 약 16 CPU초에 해당한다. 실제 서버 성능·일반 전투 비용·병렬화와 다르지만, 작은 서버 한 대로 목표를 보장해서는 안 된다는 근거다.

첫 후보는 서울 리전의 2vCPU·4GB급 Linux 서버다. 비교 기준으로 Lightsail 공식 표의 해당 IPv4 요금은 월 $24이지만, 지속 CPU 성능·리전별 전송량·세금·환율·추가 저장 비용은 계약 시 다시 확인한다. [Lightsail 요금](https://aws.amazon.com/lightsail/pricing/)

실제 입장 상한은 P0·P6의 결과로 정한다. 전투 수용량, 서버 송신량, 고스트 저장량을 함께 계산하고 월 10만 원을 우선한다. 비용이 예상치를 넘으면 신규 입장을 줄이며 진행 중 경기를 임의로 끊지 않는다. 대기 중에도 기존 혼자하기와 기록 조회는 사용할 수 있어야 한다.

**데이터 보존과 복구**

- 경기 결과·개인 최고·시즌 기록은 사용자 삭제 또는 운영상 정당한 기록 취소 전까지 보존한다.
- 일반 고스트는 7일, 현재 시즌 최고 기록은 시즌 동안, 종료 시즌 최고 기록은 종료 후 90일 보관한다. 만료된 고스트는 점수와 함께 삭제하지 않고 재생 만료 상태로 표시한다.
- 서버 재전송 대기 자료는 서버 저장 확인 전까지 보존한다. 확인 후에는 정해진 정리 주기로 삭제한다.
- 초기 복구 목표는 데이터 **RPO 24시간 이하, RTO 4시간 이하**다. 일반 재시작·배포로 완료 기록을 잃어서는 안 된다.
- 일일 백업 7개와 주간 백업 4개를 암호화해 서비스 본체와 독립된 위치에 보관한다. 복구 코드를 포함한 인증 자료는 공개 로그·고스트에 넣지 않는다.
- D1의 일반 Time Travel 기능과 Sites 사용자가 실제로 사용할 수 있는 복구 권한은 별개로 검증한다. 복구 경로를 확보하지 못하면 독립 관리 D1로 전환한다. [D1 백업·복구 문서](https://developers.cloudflare.com/d1/reference/time-travel/)
- 저장 용량은 경기 시작 전에 여유를 확인한다. 보존 약속을 지킬 수 없으면 신규 온라인 경기를 제한하며 기존 자료를 몰래 삭제하지 않는다.

**배포와 버전**

게임 규칙 버전, 통신 버전, 고스트 포맷, 콘텐츠 식별자, 배포 해시를 구분한다. 해시는 배포 정합성을 확인하는 수단이며 브라우저가 정직하다는 증명으로 사용하지 않는다.

배포는 신규 입장 중지 → 기존 경기 종료 대기 → 검증된 후보 전환 → 실제 URL 확인 순서로 진행한다. 변경된 데이터베이스 스키마는 이전 실행물과 일시적으로 공존할 수 있도록 추가형으로 적용한다. 실패한 배포에서 이미 적용된 마이그레이션도 확인한다.

[배포 자료 보관 규칙](D:/Antigravity/NewProject/docs/ARTIFACT_RETENTION.md)에 따라 정상본을 먼저 보존하고 후보 검증 후 교체한다. 성공 확인 뒤 이전 실행물·대응 검증 자료·임시 백업을 정리한다. 진행 중 배포의 짧은 공존 외에 이전 실행물을 영구 보관하지 않는다.

플레이어 데이터와 그 복구용 백업은 배포 자료가 아니다. 구형 고스트는 호환 판독 코드로 지원하고, 이를 위해 구형 게임 실행물을 무기한 남기지 않는다.

Sol 6.1은 내부 클래스 배치, 직렬화 최적화, 테스트 도구 구성은 자율적으로 개선할 수 있다. 변경 이유와 증거를 문서에 남긴다. **기존 솔로 동작·저장 호환성, 서버의 결과 판정 권한, 게스트 참여, 함께 멈추는 협동, 예산 우선, 검증 후 배포 교체**는 변경해서는 안 되는 기준이다.

초기 범위에서는 자동 매칭·채팅·상점·길드·다중 리전·기존 전체 프로필의 자동 클라우드 동기화를 제외한다. 핵심 온라인 플레이가 완성되기 전에 이를 추가하지 않는다.

이번 단계에서는 실제 Sites 배포, Linux 동시 부하, 실물 모바일과 2인 사람 플레이를 확인하지 않았다. 가장 큰 잔여 위험은 네트워크 상황에서의 조작 감각과 예산 안의 전투 수용량이며, 두 항목은 P0에서 먼저 검증한다.
