# Sol 6.1 실행용 온라인 수정 계획

> 후속 구현: F1~F7 수정·회귀 및 실제 Sites 검증 결과는 [Sites 구현·검증 보고서](SITES_IMPLEMENTATION_REPORT.md)를 따른다. 아래는 수정 전 인계 계획을 보존한 것이다.

> 2026-10-17 아키텍처 변경: F1~F7 수정 요구는 유지한다. 다만 실행 우선순위와 호스팅·저장 책임은 [Sites 중심 재검토](SITES_ARCHITECTURE_REVIEW.md)의 결함 의존성/P0~P3를 따른다. Linux/Caddy 호스트 확보를 필수 선행 조건으로 삼지 않으며, F4~F6은 Sites 기준 영속화와 함께 수정한다. 기존 감사 원문과 증거는 보존한다.

기준: [독립 감사 보고서](ONLINE_INDEPENDENT_AUDIT.md), 2026-10-16. 이 문서는 수정 지시를 실행 가능한 순서로 정리한 인계물이다. 이번 감사에서는 제품 코드를 수정하지 않았다. 기존 미커밋 변경과 정상 `build/current`/`web`를 보존한다.

## 작업 원칙과 범위

- 기존 `RunModel`, `OnlineClient`, `Store`, Sites route를 고친다. 새로운 계정 체계·프레임워크·상시 보관용 구버전 아카이브는 만들지 않는다.
- 익명 게시판, 서버 권위, 기기 개인 기록, 기존 오프라인 저장/고스트 호환성은 유지한다.
- 아래 결함의 재현을 먼저 일반 회귀 테스트로 옮긴다. 감사 재현 스크립트는 현재 결함을 관찰/일부 assert하는 도구이므로 수정 후 그대로 통과시키는 것을 목표로 삼지 않는다.
- 네트워크 프로토콜·결과 해시·고스트 상태 변경은 버전/구형 데이터 호환성을 함께 정한다. 웹과 Windows를 같은 계약으로 빌드한다.
- 완료 판정은 코드 존재, 자동 검사, 실제 클라이언트, 원격 배포를 구분한다. 현재 문서의 20Hz 기체 궤적·시즌 확정 축소도 변경 이력에 남긴다.

## 1. 입력과 재접속 복구 — F1, F2, F3, F7

영향 파일: `server/match_server.gd`, `scripts/online_client.gd`, `scripts/main.gd`, `scripts/online_motion.gd`, 필요 시 `online_config.gd`; `tests/test_online_*`와 `server/test/integration.test.mjs`.

1. 마지막 input 시각을 heartbeat와 분리한다. 250ms 후 이동/버튼을 중립화한다. 화면 이탈/포커스 상실의 중립 입력을 추가하되 서버 검사를 대체하지 않는다.
2. 최신 이동과 미소비 버튼을 분리한다. 버튼의 aim/실행 ID, seq/ACK와 중복 소비 규칙을 정한다. 같은 틱의 true→false가 true 실행을 없애지 않게 한다.
3. live snapshot에 예측에 필요한 정확한 dash 시간/방향을 넣는다. `GhostReplay.restore()`가 예측 상태를 완전히 표현한다고 가정하지 않는다. 기존 로컬 고스트 판독기는 유지한다.
4. ended 재접속은 result를 재송신한다. 경기 ID 기반 HTTP 결과 복구를 공통 클라이언트에 연결하고 결과 저장/이력/등록을 멱등 처리한다. 새로고침과 앱 재시작 지원을 약속하면 만료 있는 세션 자료를 기기에 보관한다.

완료 조건: 버튼 연속/중복/지터, heartbeat-only, 돌진 마지막 틱, 결과 메시지 유실, 방 종료 뒤 조회를 자동 검사. 실제 웹+Windows에서 입력/메뉴/단절/복귀/결과까지 확인. 세션 재시도 타이머도 `leave/join` 시 초기화 여부를 함께 점검한다(감사 재현에서 leave 후 29.5초/0.8초가 남는 것을 관찰했으며 독립 출시 차단 항목으로는 세지 않았다).

## 2. 결과·고스트 저장 경계와 전역 조회 — F4, F5

영향 파일: `server/contract.mjs`, `server/store.mjs`, `server/schema.sql`, `server/gateway.mjs`, `server/ranking/app/[...path]/route.ts`, `server/ranking/db/schema.ts`와 추가형 migration, `scripts/online_replay.gd`, 결과/이력 UI 및 백업 도구의 호환성.

1. 불변 경기 결과의 멱등 확정과 고스트 업로드/완료 상태 갱신을 분리한다. 점수는 먼저 D1에 보존한다.
2. `result_hash`에 들어가는 불변 필드를 정하고 기존 레코드·재전송 파일과 충돌하지 않는 경로를 둔다. 단순 status 변경 후 전체 해시 재계산으로 기존 경기 ID를 충돌시키지 않는다.
3. pending/complete/failed/expired를 UI와 API에서 구분한다. 완료는 청크 크기/해시 검증 뒤에만 전환한다. 파일 실패가 점수 재전송 전체를 영구 봉쇄하지 않게 한다.
4. 랭킹·경기 상세·고스트 manifest/청크의 데이터 출처를 일치시킨다. Sites 우선, 검증된 로컬 캐시는 명시적 장애 대안으로 둔다. 클라이언트는 운영 비밀 없이 동일 API를 이용한다.

완료 조건: D1 장애, R2 장애, missing/corrupt chunk, 중복/서로 다른 결과, 프로세스 종료를 주입해 점수 한 건 보존과 상태 전이를 확인한다. 빈 로컬 DB의 새 gateway에서도 기존 Sites 경기·고스트를 조회해야 한다. 백업/복원이 새 상태와 과거 기록을 모두 읽어야 한다.

## 3. 실패 경기 정리와 운영 통제 — F6, G2, G3

영향 파일: `gateway.mjs`, `store.mjs`, `match_server.gd`, 운영 문서, Sites 비공개 관리 route/정책 및 서버 환경.

1. 활성 방, 미전송 outbox, 완료/보존 대상, failed/orphan을 구분한다. 활성·미전송 자료를 보호한 상태에서 유예가 지난 고아 파일만 정리한다. 경로를 데이터 디렉터리와 정해진 경기 ID 형식으로 제한한다.
2. 실행 중 경기의 예상 최대 용량을 반영하고 용량 임계 시 새 입장만 막는다. crash 후 재시작해도 orphan 때문에 영구 포화되지 않게 한다.
3. 공개 Sites API에도 실제 지원하는 요청 제한/비용 통제를 검증한다. 최소 비공개 운영자 숨김/차단과 감사 기록을 제공한다. 계정 기반 사용자 랭킹은 만들지 않는다.
4. 업로드 대기 개수·최장 지연, 고스트 실패/고아 bytes, active rooms, tick lag, DB 오류, 백업 마지막 성공/복구 실패를 운영자가 확인할 수 있게 한다. 새 관측 플랫폼 도입이 필수는 아니다.
5. 독립 위치 백업 일정과 보존을 구성하고 데이터가 있는 격리 환경으로 복원한다. D1 페이지 export의 일관성과 R2 미백업 범위를 명시한다. RPO24h/RTO4h를 실제로 측정한다.

완료 조건: 파일 기록 도중 강제 종료와 재시작, 임계 용량, failed replay, backlog 상태에서 정리를 실행한다. 정상·미전송 기록 손실 0, orphan 회수, 신규 입장 재개를 확인한다. 운영 비밀이 웹/Windows 배포물과 로그에 포함되지 않아야 한다.

## 4. 설계 변경 명세 확정

| 결정 | 권장 방향 | 영향 |
|---|---|---|
| 20Hz 기체 궤적 → 전체 5Hz | v1 축소는 가능. 돌진/교차 이동/짧은 객체의 실제 관전 품질 검사 후 명시 | 기록 크기·재생 품질. 20Hz나 완전 재현으로 표시 금지 |
| 공통 미션 → 개인 미션 | 기존 개인 RNG 재사용 유지 가능 | 협동 설명·동시 미션 시험·공용/개인 보상 구분 |
| 24h 시즌 확정 제거 | 보상 없는 익명 게시판 v1의 과거 시즌 변경 가능 상태로 명시 | 시즌 UI/운영 기대. 확정 순위/보상 도입 때 별도 설계 필요 |
| 시각 snapshot과 live state | 렌더링 자료 재사용은 유지하되 예측 필드는 별도 보완 | 통신 버전·정확한 dash 상태·ACK |
| 점수와 고스트 독립 처리 | 점수 확정/해시와 가변 고스트 상태를 분리 | 저장 API/DB/재전송/복원 호환성 |
| top20 보존 단위 | 시즌×규칙×모드×난이도×전장, 기체 필터 포함 여부를 명시 | 현재 retention SQL은 기체별 상위20을 별도 보존하지 않음 |

이 결정들을 `ONLINE_SERVICE_DESIGN.md`와 구현 계획에 반영한다. 최초 원문을 새 내용으로 덮어써 과거 약속을 숨기지 않는다. 사용자에게 이미 합의된 익명 게시판/GitHub 배포를 다시 확인받을 필요는 없다.

## 5. 원격 제한 베타 게이트

선행: 1~3의 회귀 검사 통과, 실제 Linux 호스트와 HTTPS/WSS 주소 확보. 호스트 이름 문자열만 만드는 것은 서버 확보가 아니다.

| 게이트 | 반드시 남길 증거 |
|---|---|
| 실제 배포 실행 | Linux 전용 실행물+Caddy+systemd 기동, 정상/강제 종료, 자동 재시작, 권한/데이터 경로 |
| 세 조합 | 웹↔웹·Windows EXE↔Windows EXE·웹↔Windows EXE 각각 전투/선택/구조/결과/등록/관전. 에디터 main-pack으로 대체 금지 |
| 게임 콘텐츠 | 세 기체/세 전장/네 난이도, 진화·전술·공용/개인 파츠·동시 죽음·최종 작전. 합성 자동 검사와 사람 완주 구분 |
| 네트워크 | RTT80ms/지터20ms/손실1%에서 입력 p95≤150ms, 보정 p95≤13px/p99≤52px. RTT200ms/손실3%에서 경고/복구/안전 중단 |
| 서버 수용량 | 최대 밀도+고스트 기록 12h, CPU 여유≥30%, 메모리≤70%, 지속 틱 밀림 없음. 2방부터 측정, 50명 목표를 검증 전 개방 금지 |
| 클라이언트 | Chromium/Firefox 및 실물 Android/iOS Safari, 터치/회전/백그라운드·새로고침·소리·재생 탐색 |
| 복구/비용 | 유효 점수의 비어 있지 않은 복원, 독립 백업, 업로드 재시도 회복, 보존 약속·트래픽·저장비 측정 |

WSS가 실제 조작감 기준에 실패할 때만 WebRTC와 네이티브 확장/TURN 비용을 검토한다. 미측정 상태에서 전송 프레임워크부터 교체하지 않는다.

## 6. 후보 검증과 공개 승격

실제 주소와 호환 버전을 설정한 뒤 후보를 다시 만든다. 이번 감사의 해시 일치는 이전 후보의 출처 증거일 뿐 수정 후 검사 통과가 아니다. 변경된 자동 검사와 기존 게임 필수 검사를 실행하고 Windows/Web/Linux의 동일 소스 출처를 고정한다.

`ARTIFACT_RETENTION.md`에 따라 정상본 보존 → 후보 필수 검사·export·실행 → 공개 전환·다운로드 해시/실제 플레이 확인 → 이전 배포·대응 증거·임시 자료 정리 순서를 지킨다. 실패한 후보로 current를 교체하지 않는다. 이미 정책으로 차단된 기존 삭제 작업은 감사 범위에서 재시도하지 않는다.

최종 인계에는 수정한 F번호, 각 회귀 검사 결과, 원격/GUI/실물 검사 범위, 확정 입장 수, 잔여 제약을 남긴다. **F1~F6 미해결 또는 G1~G3 증거 부재 상태에서는 공개 서비스 완료로 표시하지 않는다.**
