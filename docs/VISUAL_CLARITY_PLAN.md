# 전체 객체 선명도와 플레이어 선체 개선 계획

작성일: 2026-10-16. 상태: **구현·로컬 검증·최신본 교체 완료**. 실제 선택한 필터/DPR, 검사 결과와 확인 한계는 [구현·검증 보고서](VISUAL_CLARITY_IMPLEMENTATION_REPORT.md)를 따른다. 사용자의 최종 시각 수용과 실물 장치 검증은 별도다.

아래는 승인 당시 계획이다. 기준 소스는 `88ce1a5024f02a6041a547e27cfc1e1770b21ea8`, 당시 검증 세대는 `3.19 / audit-20261014`였다. 후속 “계획대로 진행해” 요청으로 구현했으며 최신 로컬 세대는 `3.19 / clarity-20261016`이다. 기존 이미지 기반 입체 SF 기체와 SVG 정보 그래픽, 청록/산호/금색 계열을 유지했다. 공개 게시/원격 push는 이번 계획 범위에서 제외했다.

## 1. 목표와 완료 범위

전투 중 플레이어, 적, 탄환, 무장, 보급품, 위험 경계가 배경과 서로 분리되어 보이게 만든다. 작은 화면과 이동·회전 중에도 실루엣과 중심부를 읽을 수 있어야 한다. 플레이어 선체는 현재보다 약 24% 크게 보이도록 한다.

완료 범위는 `ArtAssets.TEXTURES`의 전체 95개 항목(PNG 33개, SVG 62개), 그 자산을 사용하는 전투·출격 준비·도감·카드·고스트와 코드로 그리는 경계/게이지/효과다. 95개 파일을 전부 다시 제작한다는 뜻은 아니다. 각 항목의 표시 크기와 용도를 검사하고 필요한 원본·그리기 경로를 수정한 후 전체 사용처를 재검수한다. 3.19의 전술 분기·보스 코어/보호 장치·최종 작전 표시도 포함한다.

게임의 피격·공격·수집 반경, 탄 발사점과 궤도, 이동/돌진, 게임 시간·보상·RNG·저장/고스트 형식은 보존한다. 특히 `RunModel.PLAYER_RADIUS = 13.0`은 유지하고 선체의 **표시 크기만** 바꾼다.

## 2. 현재 확인한 사실과 원인 후보

현재 소스, PNG 알파 영역, 기존 검증 세대의 1600×900 및 390×844 전투 캡처와 선체 원본을 확인했다. 이번 계획 단계에서 새 런타임/실물 휴대폰 검사를 실행한 것은 아니다.

| 확인된 사실 | 선명도에 주는 영향 | 대응 |
| --- | --- | --- |
| 선체 원본은 512×512, 전투 `Motion.hull()` 인자는 42 | 원본 세부 장갑선이 작은 표시 면적에 압축된다 | 선체 크기와 작은 크기용 명암/외곽을 함께 개선 |
| striker의 알파>0 영역은 461×408 | 42 draw unit에서 실제 가시영역은 약 37.8×33.5다. 화면 픽셀 크기는 viewport 배율에 따라 달라진다 | 원본 해상도 대신 실제 가시영역을 측정 |
| XP는 512×512 중 알파>0 영역이 186×264이고 표시 사각형은 기본 18 | 가시영역이 약 6.5×9.3 draw unit에 불과하다 | 투명 여백과 크기 기준을 보정하고 작은 크기용 실루엣 적용 |
| Web `fitGame()`은 모바일에서 렌더 비율을 1로 고정한다 | 고밀도 화면에서 렌더 버퍼 확대가 경계를 부드럽게 만들 가능성이 있다 | 실제 Web에서 DPR 1 / 1.5 / 2의 품질·비용 비교 |

| 객체/적에 RGB 1을 넘는 tint와 피격 플래시를 적용한다 | 밝은 부분에서 면·경계 대비가 줄어드는 원인 후보다 | 기본 재질 명암과 피격 플래시의 최대 밝기 비교 |
| 배경의 별/성운과 작은 물체의 고주파 디테일이 겹친다 | 원본이 선명해도 전투 중 실루엣을 놓치기 쉽다 | 전경의 경계를 보강하고 배경 대비를 조정 |

미세한 원본 디테일, 투명 여백, 화면 배율, 명암/효과의 문제가 함께 있을 가능성이 있다. 전체 화면 샤픈, 원본 해상도 증가, nearest 필터 한 가지를 해결책으로 확정하지 않는다. 현재 설정만으로 특정 필터나 DPR이 유일한 원인이라고 단정하지 않는다.

네이티브 모바일 크기 캡처와 실제 Web 경로도 구분한다. `test_combat_render.gd`는 창 크기와 `touch_mode`를 설정하지만, Web 전용 `_fit_viewport()`의 `content_scale_size` 및 HTML의 DPR 경로 전체를 재현하지 않는다. 기존 세로 캡처를 실물 휴대폰의 실제 표시 크기 근거로 사용하지 않는다.

## 3. 공통 시각 기준

1. **실루엣 우선:** 외곽선, 큰 장갑 면, 코어/무장 순서로 읽히게 한다. 축소 시 사라지는 미세선은 정리한다.
2. **경계 대비:** 어두운 분리선과 제한된 재질 하이라이트를 조합한다. 모든 객체를 같은 흰 테두리나 발광 후광으로 둘러싸지 않는다.
3. **몸체와 빛 분리:** 선체/탄환의 몸체는 단단하게 유지하고 추진광·잔상·폭발의 부드러움은 보조 표현으로 둔다.
4. **위험 정보 우선:** 적탄, 공격 예고, 실제 피해 경계, 보스 약점은 장식 효과 위에서 읽힌다. 효과를 줄인 상태에서도 동일한 정보를 제공한다.
5. **색과 모양 병행:** 플레이어/적, 아군탄/적탄, 경험치/회복, 파츠 등급은 색상 외에도 실루엣·중심 기호로 구분한다.
6. **실제 표시 크기 기준:** PNG 크기나 확대 캡처의 날카로움으로 합격하지 않는다. 원래 화면 100% 배율과 이동 영상에서 확인한다.

외곽 두께의 첫 비교 범위는 약 1~2 표시 픽셀이다. 여기서 Web 표시 픽셀은 CSS px, 네이티브는 창 캡처 픽셀을 뜻한다. 실제 렌더 버퍼의 DPR과 viewport 변환을 적용해 같은 화면 두께로 맞춘다. 세부 두께와 최소 몸체 크기는 대표 장면 비교 후 확정한다.

플레이어의 52는 선형 약 23.8%, 표시 사각형 면적 약 53.3% 확대다. 커진 선체에 맞춰 추진부·포구 효과·파츠 장착 위치·돌진 잔상·주변 게이지의 **시각 앵커**를 정렬한다. 실제 탄 발사점과 피격/공격/궤도 판정은 바꾸지 않는다. 외형과 기존 13 반경의 피격 중심을 혼동하지 않도록 중심부 표현도 검수한다. 선체 확대 때문에 가까운 적탄이나 픽업이 가려지면 그리기 순서와 주변 표식을 조정한다.

픽업의 작은 몸체는 가시영역 기준으로 보정하되, 회전 중심과 위치가 튀지 않도록 기존 피벗을 보존/검증한다. 탄환/위험 경계는 판정에 맞춘 가시 크기를 우선하며, 가독성을 위해 피해 영역처럼 보이는 광원을 크게 늘리지 않는다.

## 5. 구현 순서

### 단계 1 — 원인별 기준 장면과 크기 확보

- 현재 배포본에서 동일 seed·동일 시각·동일 객체 배치의 비교 장면을 준비한다. 자산별 가시영역, 논리 크기, CSS/창 크기, backing buffer, DPR, viewport 변환을 기록한다.
- 3기체·3전장, 정상/이동/45도 회전, 흡수막·피격·돌진·전술, 보스/최종 작전, 작은 픽업과 조밀한 전투를 포함한다.
- Web 가로/세로 경로를 실제 브라우저로 검사한다. 네이티브 크기 변경 fixture는 Web 경로와 구분하고, 공통 viewport 설정을 재현하도록 보완한다.

### 단계 2 — 대표 장면의 플레이어와 공통 경계

- 42→52 선체와 연결된 시각 앵커를 조정한다.
- 플레이어·일반 적·적탄·XP/회복의 대표 자산으로 현재/경계 강화/필터 후보를 비교한다. 선명한 원본이 이미 있는 부분은 재사용한다.
- 몸체 알파 가장자리와 명암을 먼저 보완하고, 원본에 포함할 외곽 처리를 우선한다. 같은 공유 CanvasItem의 filter 속성을 매 draw 호출마다 바꿔 객체별 필터가 적용된다고 가정하지 않는다.
- linear 및 mipmap 후보는 작은 크기·회전·정지에서 비교한다. nearest는 계단/점멸을 함께 확인하는 비교 후보이며 일괄 기본값으로 확정하지 않는다.

### 단계 3 — 전체 객체와 모든 사용처 적용

- 대표 장면에서 정한 기준을 전체 95개 자산과 코드로 그리는 객체에 적용한다. 목록에 정상/예고/피격/활성/소멸 및 UI/리플레이 사용처를 연결하고 누락을 체크한다.
- 여백 보정은 `art_source/prepare_assets.py`의 기존 제작 경로를 재사용한다. 작은 표시에서 구조가 무너지는 자산만 단순화/재제작하고 생성 원본·도구를 남긴다.
- 240적/240탄/300경험치에 객체마다 별도 노드나 다중 샘플 outline pass를 추가하는 방식은 피한다. 기존 묶음 그리기와 추진광 instancing을 보존한다.
- 플레이어만 추가 외곽 처리가 필요한 경우 제한된 비용으로 비교한다. 실체를 가진 물체와 부드러운 FX는 서로 다른 알파/명암 기준을 유지한다.

### 단계 4 — 고밀도 Web의 렌더 해상도 결정

- 모바일 DPR 1, 최대 1.5, 최대 2를 같은 CSS 크기·같은 장면에서 비교한다. 1→1.5는 렌더 픽셀 약 2.25배, 1→2는 약 4배이므로 화질만 보고 2를 고정하지 않는다.
- 기본 상한의 1차 후보는 1.5다. 실제 부하·메모리·가열/프레임 결과가 기준을 만족하는 경우에만 채택한다. 부하가 맞지 않으면 DPR 1에서도 자산/외곽 개선으로 가독성을 확보하고 제한을 기록한다.
- CSS 위치와 Godot 입력 위치의 일치를 확인한다. 가로/세로 회전, 드래그 이동, 방향 돌진, 두 번 탭, 하단 버튼과 선택 카드에 회귀가 없어야 한다.
- 새 화질 설정 화면이나 자동 해상도 전환 체계는 이번 범위에 추가하지 않는다.

### 단계 5 — 회귀·품질 검수 후 후보 배포

- 아래 완료 기준을 통과한 후 기존 빌드 파이프라인으로 Windows/Web 후보를 만든다. 정상 최신본 보존→후보 전체 검사→내보내기/실행→해시→교체 순서를 따른다.
- 공개 게시/원격 push는 이번 계획 범위에 포함하지 않는다. 후속 구현 단계의 배포 범위에 따라 수행한다. 기존 정책 차단 임시 자료는 재삭제하지 않는다.

## 6. 완료 판정과 검증

| 영역 | 검사와 합격 기준 |
| --- | --- |
| 정지 화질 | 같은 장면의 전/후 원본 크기 캡처에서 플레이어·적·적탄·픽업 경계와 중심이 배경 위에서 구분된다. 확대 캡처만으로 합격하지 않는다 |
| 이동 화질 | 0/45/90도와 회전/이동 영상에서 외곽의 점멸·계단·알파 프린지·과도한 하이라이트가 없다 |
| 플레이어 확대 | 같은 출력에서 선체 가시영역이 의도한 약 24% 증가하고 피벗·포구/추진부·조합 파츠·게이지가 어긋나지 않는다 |
| 판정 정합 | 플레이어 반경 13, 적/탄환/위성/위험 반경과 실제 모델 상태가 유지된다. 탄 중심과 예고/피해 경계가 판정을 잘못 안내하지 않는다 |
| 전체 커버리지 | 95개 자산과 코드 객체의 검수표에 사용처/상태/결과가 있으며 전술·최종 작전·신구 고스트까지 누락이 없다 |
| 화면 크기 | Windows 1600×900·960×540·1920×1080 및 비정수 배율, Web 390×844·844×390·320×568·568×320, DPR 1/1.5/2를 구분해 검사한다 |
| 입력/레이아웃 | 실제 뷰포트/브라우저 입력으로 선택과 복귀가 된다. 핵심 선택 화면에 스크롤을 추가하지 않는다. 회전 시 상태·피벗·터치 좌표가 유지된다 |
| 프레임 성능 | 동일 장비/장면에서 변경 직전 baseline과 변경 후 300샘플×3회 p95 중앙값을 새로 측정한다. 전체 전투/렌더/HUD/고스트의 회귀 10% 이내와 기존 스트레스 프레임 예산을 모두 확인한다 |
| 메모리/다운로드 | 기존 128MiB 텍스처 예산 내에서 확인하고, 텍스처/렌더 타깃/정적 할당/다운로드 증분을 별도로 기록한다. DPR 비용을 텍스처 메모리 수치 하나로 판단하지 않는다 |
| 저장/재생/규칙 | 기존 모델·전투·오디오·저장·고스트·모바일·아트/터치 회귀 통과, 검증 fixture의 원시 값과 source/output 해시 일치 |
| 사람의 시각 확인 | 작은 화면과 혼잡 장면에서 사용자가 실제로 더 잘 구별하는지 확인한다. 자동 이미지 수치·테스트 개수를 미적 수용의 대체 근거로 사용하지 않는다 |

최근 native 전체 전투 p95 중앙값 9.546ms는 참고 기록이다. 구현 성능 비교의 baseline으로 과거 값만 재사용하지 않고 변경 직전 같은 장비/조건에서 다시 측정한다. Web 모바일·저사양 장치의 성능은 native GPU 수치로 보장하지 않는다.

기존 `test_art.gd`, `test_combat_render.gd`, `test_performance.gd`, `test_replay_world.gd`, `test_pregame.gd`와 `tools/build.ps1`을 재사용한다. 자산 존재/치수 검사만 늘리는 대신, 가시영역·피벗·화면 변환·실제 입력·동일 모델 상태를 확인하는 회귀를 보완한다. 기대 상수나 체력 증대로 테스트를 통과시키지 않는다.

## 7. 예상 변경 위치와 산출물

- `scripts/main.gd`, `scripts/art_motion.gd`: 전투 선체 크기, 시각 앵커, 그리기 순서, 상태 표현.
- `scripts/art_assets.gd`, `scripts/ui_glyph.gd`, `scripts/item_catalog.gd`: 공통 자산 사용/표시 기준과 UI/월드 사용처.
- `assets/art/ships`, `enemies`, `objects`, `fx`, `ui`, `world`: 필요한 외곽/명암/여백 개선. 기존 자산 ID와 역할 유지.
- `art_source/prepare_assets.py`, 필요한 제작 원본: 재현 가능한 자산 보정. 투명 경계의 RGB/알파와 회전 피벗 검수.
- `web/index.html`, `project.godot` 및 필요한 import 설정: 검증 후 결정한 DPR/필터/mipmap 설정만 변경.
- `scripts/space_backdrop.gd`, `assets/art/space_flow.gdshader`: 배경 대비 조정이 필요한 경우 기존 경로에서 보완.
- 위 회귀 테스트, 최신 규칙/검증 문서: 실제 변경 범위와 검증 한계를 반영.

완료 산출물은 실행 가능한 후보 Windows/Web, 전체 객체 검수표, 같은 조건의 전/후 원본 캡처·짧은 이동 영상, 원시 성능/메모리 결과, 소스/출력 해시와 검증 보고서다. 구버전 배포본을 별도 상시 아카이브로 남기지 않는다.
