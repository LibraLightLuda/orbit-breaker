# Orbit Breaker 온라인 서비스 독립 기술 감사

감사일: 2026-10-16 KST. 기준 작업본: `D:\Antigravity\NewProject`, Git HEAD `88ce1a5`와 감사 시작 시의 미커밋 변경 전체. 대상은 공식 솔로·2인 협동·익명 랭킹·온라인 고스트·운영 경로다. 예상 규모는 한국 중심 동시 50명 **목표**, 초기 설정 2방이며 실제 운영 수용량으로 인정하지 않는다.

## 판정

**현재 공개 온라인 서비스 개통은 보류한다.** 서버 권위 판정, 공통 Godot 클라이언트, 익명 경기 게시판, Sites 저장소의 큰 방향은 타당하다. 그러나 독립 재현에서 입력 유실·이동 중립화 실패·완료 결과 복구 누락·고스트 오류에 의한 점수 전송 차단·전역 고스트 조회 단절·고아 파일 누적·이동 예측 오차가 확인됐다. 단순히 호스트 주소만 설정해 공개할 상태는 아니다.

P0는 즉시 데이터 파괴 또는 광범위한 권한 탈취, P1은 공개 전 해결할 게임/데이터/가용성 결함, P2는 제한 베타 전 해결하거나 명시적으로 제한해야 할 품질·운영 항목으로 사용한다. 이번 감사에서 P0는 확인하지 않았다. **확인된 결함 7건: P1 6건, P2 1건.** 별도로 운영 차단 조건 3개와 설계/검증 위험을 기록한다. 취향·코드 스타일 리팩터링은 요구하지 않는다.

구현 파일은 수정하지 않았다. 감사 시작 시 추적·비추적 파일 995개의 해시를 기록했고 기존 파일 변경 0개를 확인했다. 감사 문서·격리 재현 스크립트·증거만 추가했다. 빌드 교체, 외부 점수 게시, 배포, DB 복원, 기존 자료 삭제를 하지 않았다.

## 확인된 결함

### F1 — P1 · 함께 도착한 입력에서 돌진·오버드라이브가 사라짐

- **영향:** 공식 솔로/협동의 모든 클라이언트. 지터·일시 정체로 두 입력이 한 서버 프레임에 도착하면 실제 누른 버튼이 적용되지 않을 수 있다. 점수가 서버에서 계산되어도 조작의 공정성은 깨진다.
- **근거:** `server/match_server.gd:82–97, 133–138, 194–200`. 패킷 큐를 먼저 모두 비운 뒤 틱을 진행하고, 매 입력이 `slot.input` 전체를 대체한다. `scripts/online_client.gd:66–68`, `scripts/main.gd:2497–2506`은 버튼을 한 입력에만 싣는다.
- **재현/관찰:** `repro-model.gd`가 원본 `handle()`에 seq1 dash/overdrive=true, seq2=false를 틱 사이에 연속 전달. 실제 저장 입력은 둘 다 false다. 네트워크를 조작하지 않아도 패킷이 묶여 수신되는 정상 상황과 같은 처리 순서다.
- **원인:** 이동의 최신 상태와 한 번 실행할 버튼을 동일한 덮어쓰기 값으로 취급한다.
- **최소 수정:** 이동은 최신 값 유지, 버튼은 틱에서 소비할 때까지 누적하고 해당 버튼 시점의 aim을 보존한다. 재전송/재접속까지 지원하려면 실행 ID와 처리 ACK를 함께 정의한다. 받은 seq와 적용된 이벤트를 혼동하지 않는다.
- **검증:** 두 입력/역방향 aim/중복 seq/재접속을 넣어 돌진·오버드라이브가 정확히 한 번 실행되는 회귀 검사. 60Hz 두 클라이언트 + 지터에서 실제 거리와 쿨다운 대조.

### F2 — P1 · heartbeat가 오래된 이동을 계속 유효하게 만듦

- **영향:** 메뉴·포커스 전환·입력 전송 중단 때 의도치 않은 이동과 사망. 상대방도 잘못된 이동 상태를 보게 된다.
- **근거:** `server/match_server.gd:94–97`은 ping 포함 모든 Dictionary에서 `peer.last`를 갱신한다. `:135`의 250ms 입력 유효성 판단도 같은 값을 쓴다. `online_client.gd:79–82`의 ping은 이동 입력과 별도로 계속된다. `main.gd:2498`은 playing 화면 외에는 입력을 보내지 않는다.
- **재현/관찰:** 실제 원본 경기 서버에서 move=[1,0]을 한 번 보내고 100ms마다 ping만 전송. 약 1.1초 후 x가 **239.79px** 증가했고 speed **217.96px/s**, ACK=1을 유지했다. 입력 중단 250ms 후 정지가 아니다.
- **원인:** 연결 생존 시간과 마지막 유효 입력 시간을 하나로 관리한다.
- **최소 수정:** slot별 마지막 검증된 input 시각을 별도로 저장해 250ms 경과 시 이동/버튼을 중립화한다. 클라이언트의 게임 화면 이탈·포커스 상실에도 중립 입력을 보내되 서버 시간 검사를 필수로 유지한다.
- **검증:** ping은 살아 있으나 input이 300ms 이상 없는 경우 정지, 정상 60Hz 입력은 이동, 복귀 시 최신 입력으로 재개. 무기도감/창 전환도 실제 GUI에서 검사한다.

### F3 — P1 · 종료 직후 연결을 잃으면 저장된 결과를 복구하지 못함

- **영향:** DB에는 완료 기록이 있지만 사용자는 결과 화면·기기 온라인 이력·등록/관전 버튼을 잃는다. DB 데이터 자체가 삭제된 것은 아니다.
- **근거:** `match_server.gd:155–184`는 started이면 항상 begin만 전송한다. `:98–103`은 ended 상태에서 상태/결과 재송신 없이 30초 뒤 종료한다. `online_client.gd`의 room/resume은 메모리뿐이며 `main.gd:2482–2489`에서 result 메시지를 받아야 이력을 저장한다. gateway의 `/v1/runs/:id`를 결과 복구에 연결한 클라이언트 경로가 없다.
- **재현/관찰:** 2초 fixture 완료 후 소켓을 닫고 동일 resume으로 접속. HTTP 경기 조회는 **200**, 새 소켓은 **hello, begin**만 수신했다. 재전송 검사는 완료 이벤트 유실 상황의 서버 동작을 직접 확인한다.
- **원인:** 진행 경기 재접속과 완료 결과 재조회가 같은 분기로 처리되며 완료 응답의 재시도 계약이 없다.
- **최소 수정:** ended면 보존한 result를 재송신하고, 클라이언트는 입장 시 받은 경기 ID로 완료 여부를 조회·복구한다. 새로고침까지 약속한다면 활성 경기 ID와 만료 있는 resume을 기기 세션에 보존하고 종료 시 지운다. 영구 계정은 필요 없다.
- **검증:** 결과 직전/직후 연결 차단, result ACK 유실, 방 프로세스 종료 후 재조회, 앱 재시작/브라우저 새로고침. 이력/등록은 중복 없이 한 건이어야 한다.

### F4 — P1 · 고스트 오류가 확정 점수의 Sites 전송까지 막음

- **영향:** 점수는 로컬에 남지만 전역 랭킹에 영구 반영되지 않을 수 있다. UI가 재시도 중이라고만 보이면 운영자가 결과를 잃은 것으로 오인한다.
- **근거:** `gateway.mjs:60–80`은 complete 고스트의 모든 파일 읽기·해시 확인·업로드가 끝나야 `/internal/results`를 호출한다. 한 청크의 ENOENT/손상/R2 장애가 매번 같은 catch로 돌아간다. `result_hash`는 현재 replay 내용까지 포함하므로 단순히 retry에서 status만 바꾸면 중복 충돌을 만들 위험도 있다.
- **재현/관찰:** 유효한 완료 점수 outbox와 존재하지 않는 청크 한 개를 준비해 원본 gateway 시작. 초기/5초 재시도 후 로컬 경기 조회 **200**, 가짜 Sites에는 retention만 도착하고 **results 호출 0회**. 오류 로그에 ENOENT가 남는다.
- **원인:** 점수 확정과 파일 완료를 하나의 업로드 순서/실패 단위로 결합했다.
- **최소 수정:** 불변 경기 결과를 먼저 멱등 저장하고 고스트는 pending/complete/failed로 독립 갱신한다. 점수 해시와 가변 고스트 상태의 경계를 정하고 기존 저장 해시를 보존하는 호환 경로를 둔다. 완료 표시 전 모든 청크의 크기/해시를 검증한다.
- **검증:** 청크 누락·해시 불일치·R2만 실패·D1만 실패·중간 종료를 각각 주입. 점수는 정확히 한 번, 고스트는 완료 전 재생 금지, 복구 후 상태 갱신 및 재시도 종료.

### F5 — P1 · 전역 랭킹과 경기/고스트 조회의 데이터 출처가 다름

- **영향:** 서버 교체/빈 로컬 DB 복구/여러 gateway가 생기면 글로벌 순위는 보여도 해당 경기 고스트를 열 수 없다. R2에 파일이 정상 보존되어 있어도 실패한다.
- **근거:** `gateway.mjs:168–173`은 Sites 랭킹을 읽지만 `:180–188`은 경기/고스트를 로컬 Store와 파일에서만 읽는다. 클라이언트 `main.gd:2554–2576`과 `online_replay.gd:46`은 같은 gateway 주소를 사용한다. Sites에는 replay GET이 있으나 gateway fallback이 없다.
- **재현/관찰:** 로컬 DB가 빈 원본 gateway에 경기와 manifest를 반환하는 가짜 Sites 연결. 순위는 **200/storage=sites**, 동일 ID의 고스트 manifest는 **404**였다. 이는 실제 공개 저장소에 새 기록을 쓰지 않은 격리 재현이다.
- **원인:** 글로벌 저장소를 조회하는 경로가 랭킹에만 적용됐다.
- **최소 수정:** 전역 경기/고스트 조회를 Sites로 일관되게 전달하고 검증된 로컬 캐시는 장애 시 명시적 fallback으로 사용한다. Sites 경기 상세 조회 계약도 추가한다. 다운로드 제한·해시 검사는 유지한다.
- **검증:** 서버 A 경기 후 빈 서버 B로 교체, 로컬 파일만 삭제한 격리 환경, Sites 장애와 stale cache, 이미 만료된 고스트. 결과/고스트 상태가 모순 없이 표시돼야 한다.

### F6 — P1 · 중단/실패 경기의 고아 고스트가 용량을 영구 점유

- **영향:** 장애가 반복되면 입장이 영구 503이 되어 서비스가 멈출 수 있다. 새 경기를 막는 용량 제한 자체는 정상 방어다.
- **근거:** `match_server.gd:279–307`은 경기 중 파일을 기록하지만 `abort():331–334`는 결과/정리 표식을 만들지 않는다. `gateway.mjs:88–96`은 DB의 complete/만료 대상만 삭제하고 모든 replay 디렉터리를 용량에 포함한다. `store.mjs:37–43`은 failed 또는 DB에 없는 경기 파일을 찾지 않는다.
- **재현/관찰:** 프로세스 장애 후 잔여를 모사한 DB 없는 오래된 replay 청크 128bytes와 검사 전용 64bytes 제한. startup maintenance 후에도 신규 방은 **503**. 용량 수치를 축소한 경계 검사이며 실제 10GiB를 채운 부하 시험이 아니다.
- **원인:** 활성·전송대기·실패·고아 파일의 수명주기가 완료 경기 DB 레코드에 종속된다.
- **최소 수정:** 활성 방과 미전송 결과를 보호하면서 orphan/failed를 유예 후 회수한다. 진행 중 허용량도 예약/회계에 반영한다. 파일 보존·재전송·청소의 순서와 crash 복구 조건을 명시한다.
- **검증:** 청크 기록 후 강제 종료, 결과 rename 직전 종료, replay failed, 재시작, 디스크 한계. 재전송 대기 결과/정상 완료 고스트를 삭제하지 않고 고아 자료만 회수해야 한다.

### F7 — P2 · 시각 고스트의 돌진 플래그를 실시간 예측에 사용해 거리 오차 발생

- **영향:** 지연이 있을 때 자기 기체가 과도하게 이동한 뒤 보정된다. 충돌 판정은 서버에 남아 있으므로 서버 순간이동/치트 허용으로 표현하지 않는다.
- **근거:** `ghost_replay.gd:557–561`은 dash 잔여시간 대신 bool을 저장하고 `:449`는 true를 **0.2초**로 복원한다. `main.gd:2441–2455`는 이를 실시간 상태에도 사용해 미처리 입력을 재예측한다. `online_motion.gd:16–20`은 잔여시간으로 이동 거리를 계산한다.
- **재현/관찰:** 서버 dash_time=0.01초를 snapshot/restore하면 0.2초가 된다. 같은 0.05초 오른쪽 입력을 원본 `_step_player()`와 예측에 적용하면 위치 차이 **28.88px**. 단일 합성 사례이며 네트워크 p95 측정치가 아니다.
- **원인:** 관전용 최소 표현이 예측에 필요한 상태를 잃는다.
- **최소 수정:** live state에 정확한 dash 잔여시간/방향과 ACK 의미를 추가해 복원 후 예측한다. 구형 고스트 포맷을 전역 변경하지 않는다. 상대 객체 보간은 원격 실측에 따라 별도 적용한다.
- **검증:** 돌진 시작/중간/끝, 두 기체 속도 버프, 0/40/80/200ms 지연의 authoritative 대조. 최종 RTT80/지터20/손실1%에서 위치 보정 p95≤13px, p99≤52px 확인.

## 운영 차단 조건과 미검증 위험

### G1 — 공개 전투 서비스 및 세 클라이언트 조합 미완료

`online_config.gd:4`의 공개 API_URL은 빈 값이며 운영 문서도 외부 Linux/HTTPS 호스트 미배포를 명시한다. 공개 Sites는 존재하지만 게임 방 생성/공식 솔로/협동 서비스가 개통된 것은 아니다. 실제 Windows EXE GUI를 포함한 세 조합, 10분 후반 콘텐츠/구조/선택/결과/관전, 모바일 전환·백그라운드가 필요하다. 로컬 17초 패배 완료와 EXE 리소스를 에디터로 실행한 검사는 각각 제한된 증거다.

### G2 — 수용량·WSS 조작감·비용·장시간 운영 승인 근거 부족

2방 기본 제한은 적절한 출발점이지만 부하 승인 수치가 아니다. 전체 프레임 20Hz 전송, Godot 프로세스당 비용, 로컬 동기 SQLite, Sites 순위/retention window query, 순차 청크 업로드 비용은 실제 밀도에서 측정해야 한다. 50명 또는 월 10만 원 충족을 보장할 근거가 없다. 이번 150초 soak 미완료는 별도 제한이며 원격 12시간 검사를 대신하지 않는다.

보안상 입력 정규화·패킷 상한·Caddy internal 경로 차단·HMAC·SQLite 바인딩·원본 점수 신뢰 경계는 긍정적이다. 하지만 Sites 공개 `/v1/rankings` GET/POST는 gateway의 방문자별 제한을 거치지 않으며 route 자체에도 rate limit이 없다. 대량 질의에 의한 실제 장애/비용 상승은 이번에 부하 공격으로 검증하지 않았다. 공개 익명 닉네임의 운영자 숨김·차단 경로도 구현 직전 계획에는 있었지만 현재 route/schema에는 없다. 최소 운영 통제와 알림을 준비하고 검증해야 한다. 같은 사람이 여러 경기/닉네임을 쓰는 것은 합의한 경기 게시판 모델의 특성이며 계정 기반 랭킹 부정행위로 판정하지 않는다.

### G3 — 운영 복구 계약 미완료

암호화 백업/복원 도구의 자동 검사는 통과했지만 일일7/주간4 독립 위치 일정, 비어 있지 않은 실제 D1 복구, 실제 RPO24h/RTO4h는 확인하지 않았다. Sites 조회 결과 자동 일정은 빈 배열이며 이는 외부 운영체제 cron 존재/부재의 증거는 아니다. `backup_cloud.mjs`는 페이지별 API export를 로컬 SQLite로 조립한다. 원본 D1 전체의 특정 시점 snapshot을 보장하는 구현은 아니므로 운영 중 publish/retention과의 일관성 검사를 추가한다. R2 파일은 백업되지 않는다. 점수 복구와 고스트 재생 복구의 SLA를 분리해야 한다.

## Sites 호환성 판단

[공개 랭킹 사이트](https://orbit-breaker-records.chrcra89.chatgpt.site)는 실제 익명 GET/CORS/브라우저 동작이 확인됐다. 설치된 Sites 런타임 계약은 Cloudflare Workers·D1/R2이며, 원본은 `cloudflare:workers` 바인딩과 HTTP 업로드를 사용한다. 외부 Node/Godot 서버를 별도로 두는 구조는 이에 맞는다. Sites 프로세스에서 Godot 실행을 전제하지 않는다.

[공식 Sites 문서](https://learn.chatgpt.com/docs/sites)와 [공식 생성/사용 안내](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites)는 지원 런타임·계정/워크스페이스 제약과 공개 설정의 구분을 안내한다. 이번 확인은 현재 프로젝트의 실제 public 상태와 읽기 API에 한정한다. 실제 D1/R2 쓰기·삭제를 재실행하지 않았고 기존 7항목 검사 결과는 과거 구현자 증거로 구분한다. 신규 클라우드 자원이나 권한은 만들지 않았다.

## 판정에서 제외한 가설

- 144Hz 합성 전송은 서버에서 1008로 차단됐지만 정상 클라이언트는 `main.gd:343–347`의 기본 60Hz 물리 콜백에서 전송한다. **고주사율 모니터 때문에 끊긴다는 초기 가설은 철회**했다. 테스트 결과는 과도 입력 방어의 증거다.
- 제한1방에 동시3요청을 보낸 결과는 201/503/503, 실제 rooms=1이었다. 비동기 입장 경쟁은 이번에 재현하지 못했으므로 확정 결함 목록에서 제외했다.
- 로그에 성공 문구가 없었던 soak timeout을 게임 불안정/메모리 누수로 확대하지 않았다.
- 합성 고체력 fixture는 장기 모델 경로를 실행하는 용도다. 사람 난이도·정상 체력 생존·실물 기기 검증이라고 주장하지 않는 한 테스트 조작으로 분류하지 않는다.

## 후속 조치

실행 순서와 완료 조건은 [Sol 6.1 수정 계획](ONLINE_REMEDIATION_PLAN.md)에 정리했다. 가장 작은 안전한 출시 범위는 현재 오프라인 배포를 유지하고, F1~F7과 복구 경로를 고친 뒤 실측한 2방 이하의 제한 베타부터 여는 것이다. 계정·새 프레임워크·자동매칭을 추가할 필요는 없다.

미확인: 실제 Linux/Caddy 실행, 원격 WSS·12h 부하, Windows EXE 직접 GUI 조작, 실물 모바일/Safari, 사람 2인 완주·재생 품질. 이번 결과를 해당 환경의 출시 승인으로 사용하지 않는다.

## 감사 임시 자료 정리 상태

이번 감사가 만든 운영 데이터와 무관한 Temp DB/고스트 재현 폴더의 정리 명령은 자동 승인 검토에서 `blocked by policy`로 실행 전에 거부됐다. 삭제를 우회하거나 재시도하지 않았다. OS 잠금이나 실제 권한 오류로 해석하지 않는다. 남은 정확한 경로와 사유는 [정리 상태](audits/online-20261016/scratch-cleanup.json)에 보존했다. 기존 build/artifacts와 플레이어 저장 자료는 정리 대상에 넣지 않았다.
