# Orbit Breaker 전체 그래픽 개편 — 아트 디렉션과 실행 계획

작성일: 2026-10-12. 상태: **계획 승인 대기 / 게임 구현 미착수**.

이 문서와 [전체 제작 목록](ART_ASSET_MATRIX.md), [레퍼런스 조사](ART_REFERENCE_REVIEW.md)를 함께 실행 명세로 사용한다. 이번 작업에서 게임 코드·리소스·설정·배포본을 변경하지 않았다. 이후 계획 승인은 아래 전체 그래픽 작업의 시작을 뜻하며, 대표 장면의 품질 통과를 생략하는 뜻은 아니다.

## 1. 결정한 방향

**입체감 있는 정밀 SF 기체가 붕괴하는 궤도 안에서 성장하며 외계 침공을 버티는 우주 생존 액션.**

화면의 주인공은 플레이어 기체와 그 주변에서 진화하는 무장이다. 단색 윤곽 도형을 기본으로 삼는 현재 표현에서 벗어나, 면·두께·재질이 보이는 소형 기체, 역할을 실루엣으로 구분하는 침공체, 깊이가 느껴지는 우주, 정확한 경계를 가진 에너지 공격으로 발전시킨다. 게임은 현재의 탑다운 2D 공간과 조작을 유지한다. 3D 제작 도구는 일관된 2D 스프라이트와 메뉴용 렌더를 만드는 수단으로 사용한다.

공통 조형은 **닫힌 장갑 면, 분리된 에너지 코어, 동심 궤도와 절개된 호**다. UI는 정밀 계기판, 전투 물체는 같은 구조를 실제 물체로 표현한다. 각 레퍼런스의 겉모습을 섞지 않고 이 조형 원칙으로 모두 다시 만든다. 기하학은 정보 전달에 남기고, 기체·적·설치물의 완성형 외관은 새로 제작한다.

새로운 진영·인물·문명·건물·환경 충돌물·기체 종류는 추가하지 않는다. 아래의 장갑·결정성 표면·성운 표현은 기존 게임을 위한 **미술적 해석**이며 세계관의 새 사실이 아니다. 행성 방어 외에 상호작용 가능한 행성을 추가하거나, 궤도 경계를 물리적인 벽으로 보이게 만들지 않는다.

범위를 줄이는 선택은 같은 품질 기준으로 대표 전투 장면까지 먼저 구현하는 것이다. 이는 중간 검토 범위로 사용할 수 있지만, 사용자가 요청한 전체 개편의 완료 조건을 대체하지 않는다.

## 3. 직접 실행·화면 분석 결과

### 이번 조사에서 새로 확인한 근거

- 현재 소스를 Godot 4.7.1/OpenGL 3.3/NVIDIA GeForce RTX 4070 Ti에서 실행했다. 기존 `test_uiux.gd --stage=0 --output=<임시 조사 폴더>`를 사용했고, `18/18` 확인이 통과했다. 이는 조사용 렌더 하네스 실행 결과이며 전체 제품 테스트 통과를 뜻하지 않는다.
- 타이틀·출격 준비·3기체 전투·후반 강적·강화·무기/아이템/테크 도감·업적·결과·설정·도움말을 새로 렌더했다. 타이틀·출격·후반 전투·강화·무기 도감·결과의 이미지 내용을 직접 검토했다.
- 최신 배포 증거 `artifacts/current/feedback318-960/combat.png`, `events/black_hole-active-full.png`도 직접 열어 9버프의 소형 화면 배치와 이벤트 표현을 확인했다.
- 공개 웹 3.18을 인앱 브라우저에서 열어 타이틀→출격 준비→자연 전투 진행→Space 입력→ESC 일시정지를 직접 조작했다. 고밀도 장시간 플레이나 정량 웹 FPS 검증은 아니다.
- 최신 `retention-status.json`은 `complete=true`, `remaining=[]`이다. 과거 문서·기억의 정리 차단 상태를 현재 상태로 사용하지 않는다.

### 성능 근거를 구분한다

이번 정적 렌더 하네스는 적 240·탄 240·경험치 300, 1600×900, VSync 해제, 60프레임 준비 후 180표본에서 median **19.974ms**, p95 **21.602ms**, max **23.069ms**였다. `queue_redraw()` 후 `frame_post_draw`까지 기다린 시간이며 순수 GPU 시간이나 실제 전투 전체 프레임 시간은 아니다. 현재의 시각 변경에 충분한 60fps 여유가 있다고 결론 내릴 수 없다.

최신 배포의 별도 모델 검사에 기록된 평균 4.866ms/p95 8.446ms는 이동·충돌 fixture 결과다. 이를 새 렌더 결과와 합쳐 60fps 통과로 계산하지 않는다. 이번에는 전체 회귀·내보내기를 다시 실행하지 않았다.

## 4. 통일된 스타일 규칙

### 형태·재질·조명

1. 플레이어 기체: 어두운 금속 구조 위에 밝은 세라믹 장갑 면과 제한된 색상 인서트. 외곽 실루엣, 주 기능부, 코어의 세 덩어리로 먼저 읽힌다. 작은 나사·패널선은 실루엣을 해결한 뒤 추가한다.
2. 침공체: 어두운 분절 외피 사이의 발광 코어. 추적·질주·중장·포격의 비례가 다르다. 결정성/비인간적 면은 미술적 해석이며 새 적 분류를 만들지 않는다.
3. 입체감: 공통의 부드러운 상부 조명과 얕은 음영. 소형 회전 스프라이트는 위쪽 중심 조명으로 회전 시 빛 방향 모순을 줄인다. 우주 공간에 바닥 접촉 그림자처럼 보이는 큰 검은 타원은 사용하지 않는다.
4. 발광: 코어·추진·탄환·타격 순간에 집중한다. 선체 전체 윤곽, 모든 텍스트, 모든 패널이 동시에 빛나지 않는다. 블룸을 꺼도 실루엣·상태·판정이 보이는 것이 기준이다.
5. 궤도: 게임의 고유 표식이다. 새 위성 기체와 흐름이 궤도의 성장을 보여준다. 원형 선 하나를 굵게 만드는 것으로 진화를 대신하지 않는다.

### 색상과 명도

기존 의미를 유지한다. UI의 금색 보상, 청록 경험치, 초록 돌진/회복, 적·피격의 따뜻한 색, 외곽의 청록→금→적→보라 순서는 바꾸지 않는다. 색상 외에 형태·모션 방향·표식으로 구분한다.

| --- | --- | --- |

| 선체 밝은 면/글자 | `#E9F0EC` | 넓은 흰색 발광 금지. 글자와 물체는 위치·외곽선으로 분리 |
| 스트라이커/활동 경계 | 기존 청록 계열 `#62E8D8`/`#72DCE6` | 배경 채도를 내려 아군과 같은 밝기의 성운을 피함 |

### 전장별 장면 구성

- **외곽 고리**: 넓은 어두운 여백, 비스듬히 흐르는 희박한 우주 먼지, 원거리의 짧은 궤도 잔광. 빠르게 우회하는 적의 이동이 주 시각 리듬이다. 배경 잔해는 작고 저대비이며 충돌물로 읽히지 않는다.
- **번개 회랑**: 길게 늘어진 이온 흐름과 깊이가 다른 가는 흐림층. 전역 교차 통로가 켜질 때만 실제 사각 판정 범위 내부를 연결하는 강한 전기 아크를 사용한다. 장식 번개가 공격 예고로 오인되지 않게 한다.
- **잔해 용광로**: 낮은 채도의 먼 잔해층과 큰 열광의 흐름. 난색은 밝기까지 올리지 않는다. 폭발 예고의 노란 선과 활성 코랄 영역을 배경보다 선명하게 유지한다. 새로운 운석 충돌 판정을 만들지 않는다.
- **붕괴 진행**: 모델의 시간/위험 상태로 먼 우주층의 흐름과 궤도 에너지의 불안정도를 점진적으로 바꾼다. 활동반경 축소, 실제 경계 흔들림, 새 장애물 등 규칙 변화는 금지한다. 외곽 장식이 갈라져도 안전/위험 기준선은 연속적으로 읽혀야 한다.

메뉴의 큰 기체 렌더, 전장 썸네일, 타이틀의 궤도 장면은 같은 선체·재질·공간 자산에서 파생한다. 타이틀용 장면이 실제 게임보다 다른 장르처럼 보이지 않게 한다.

### UI·텍스트·접근성

최근 UIUX의 버튼 흐름·3택 강화·페이지 도감·상단 좌/중/우 정보 영역·버프 두 줄·하단 파츠·기체 부근 스킬 게이지를 보존한다. Noto Sans KR/OFL/MSDF를 유지한다. 사진이나 생성 이미지 안에 한글을 구워 넣지 않는다.

상단 배경 12%, 토스트 배경 6%/글자 60%, 정지 버튼 28×28 등 3.17/3.18의 명시적 계약을 먼저 유지한다. 낮은 대비는 배경을 어둡고 조용하게 만들거나 글자에 작은 국소 외곽선을 주어 해결한다. 의도적으로 낮춘 알림을 다시 크게 만들지 않는다.

버튼의 기본·hover·focus·pressed·선택·잠김·disabled를 새 표면에 모두 반영한다. 960×540에서는 주요 수치·상호작용 텍스트의 실측 크기와 겹침을 확인한다. 색약/회색조에서도 아군·적탄·위험·보급을 형태로 구별한다. `reduced_motion`에서는 장식 흐름·반복 맥동·잔상·카메라 장식을 줄이고 필수 경계·진행·방향·충전·피격 원인은 남긴다.

기본 제작 경로는 **Blender 원형 → 투명 PNG/아틀라스 → Godot의 공통 2D 표시**다. 새 의존성을 설치하지 않고 재현할 수 있다. Imagegen은 선택적인 탐색 수단이다. 사용할 수 없으면 동일 설계의 Blender 모델·노이즈/그라디언트 기반 우주층으로 진행한다. 결과가 단순 도형 수준이면 이 경로를 택했다는 이유로 통과시키지 말고 대표 장면을 다시 다듬는다.

### 원본과 런타임 자산

후속 모델은 아래처럼 작은 구조로 시작하고, 실제 필요에 따라 합칠 수 있다.

```text
art_source/             # .blend, 생성 프롬프트/원본, 원본 SVG, 출처·라이선스
assets/art/ships/       # 승인된 기체와 부착물
assets/art/enemies/     # 일반/정예/지휘체
assets/art/world/       # 전장·이벤트 재질
assets/art/fx/          # 공유 스파크·충격·항적/폭발 시트
assets/art/ui/          # 아이콘·메뉴 렌더·앱용 산출물
assets/art/shaders/     # 실제 사용한 소수의 canvas_item 셰이더
```

`export_presets.cfg`가 `all_resources`이므로 원본 `.blend`가 Godot의 자동 3D 임포트를 유발하지 않게 `art_source/.gdignore`와 export 제외를 함께 적용한다. 모델은 오프라인 제작용이며 게임은 최종 2D 산출물만 읽는다. 생성 이미지가 `$CODEX_HOME/generated_images/`에만 남은 상태로 프로젝트가 참조하지 않게 한다. 외부 레퍼런스 원화는 런타임 자산으로 복사하지 않는다.

자산별로 ID, 원본, 런타임 경로, pivot, 논리 크기, 투명 여백, 상태/프레임, 사용자 화면, 제작법, 라이선스, 검사 결과를 기록한다. 재생성 스크립트가 필요한 경우 승인 후 작성하고 작동 확인을 붙인다. 지금 범용 에셋 관리 프레임워크를 만드는 것은 필요 없다.

### 해상도·프레임의 시작 규격

- 기체 원형: 256px 투명 마스터와 메뉴용 512px 렌더에서 시작. 실제 플레이는 현행 약 30~54 논리px의 몸체/부속 비례 안에서 검사한다. 모든 기체의 충돌 반경 13px는 그대로다.
- 일반 적: 128~256px 원형, 보스 512px 원형. 표시 크기는 `enemy.radius`로 결정한다. 큰 텍스처 크기를 곧 큰 게임 내 몸체로 해석하지 않는다.
- 기체의 방향은 연속 2D 회전을 우선 사용한다. 회전 조명 문제가 실제로 보일 때만 normal map 또는 제한된 방향별 프레임을 비교한다. 모든 물체에 무조건 32방향 시트를 만들지 않는다.
- 위성/소형 설치물: 128px 원형. 작은 화면에서 2~3개의 큰 면과 코어로 읽히게 디테일을 덜어낸다.
- UI: 픽토그램 24/32/48 논리px에서 검사. 원본 SVG 또는 고해상도 알파를 사용하고 선 굵기를 같은 계열로 맞춘다. 12종 보급은 같은 등급 컨테이너와 개별 심벌을 조합한다.
- 배경은 전장별 큰 형태 1장과 공유 노이즈/먼지층부터 시작한다. 큰 텍스처를 여러 겹 덧대기 전에 1024~2048 크기에서 시임·메모리·웹 로드를 확인한다.
- 아틀라스는 2048 이하 페이지로 시작하고 필터 번짐을 막는 padding/extrusion을 둔다. 2048 RGBA8 한 장은 기본 약 16MiB, mipmap 포함 약 21.3MiB이므로 모든 종류를 개별 대형 이미지로 유지하지 않는다. 실제 Godot 임포트 후 메모리를 측정한다.

이는 제작 시작값이다. 대표 장면에서 축소 품질·메모리·배칭을 비교한 뒤 바꿀 수 있다. 필터·mipmap·압축을 전역으로 무조건 켜거나 끄지 말고 작은 선·큰 배경·UI별로 확인한다.

### 코드 통합 원칙

- 규칙 소유자는 계속 `RunModel`이다. `game_content.gd`, `expedition.gd`, 저장/업적/고스트의 ID·수치·형식을 시각 개선 때문에 바꾸지 않는다.
- `main.gd`의 플레이어 그리기와 `ui_glyph.gd.ship()`의 미리보기는 같은 최종 기체 원본을 참조한다. 보급도 `ItemCatalog.draw_icon()`/`item_icon.gd`/필드/HUD/방향 표시를 함께 전환한다.
- ID→시각 자산을 연결하는 작은 공통 표와 필요한 그리기 함수만 분리한다. 대규모 씬 구조 개편이나 물체마다 새 Node를 강제하지 않는다. 기존 culling·개수 상한·공통 렌더 경로를 유지한다.
- 연속 탄환·경험치·적처럼 수가 많은 것은 아틀라스/묶음 렌더를 우선 비교한다. `MultiMeshInstance2D` 등은 해당 물체·대상 웹에서 실제 이득이 확인될 때 도입한다.
- 일시정지·강화·도감·고스트 시간 탐색은 시각 시간도 제어한다. 전투 셰이더에 무제어 `TIME`을 쓰지 말고 현재 모델/관전의 표시 시각과 reduced_motion을 전달한다. 생성/수명·기존 스냅샷 상태에서 재구성 가능한 효과를 우선한다.
- 미술 변형은 기존 개체 ID·위치·시각에 대한 결정적 해시 또는 별도 표시 전용 상태를 사용한다. 게임 RNG, 미션 RNG, 아이템 RNG를 소비하지 않는다.
- `_draw_arena(world)` 계열은 전달받은 모델을 그려야 한다. 도우미에 전역 `run` 참조가 남았는지 실제 관전 화면에서 확인한다. 과거 경로 고스트는 없는 전장 정보를 새로 지어내지 않는다.
- 실드·방벽·돌진 무적·오버드라이브는 별도 상태다. 표현의 통합이 서로 다른 방어 규칙을 하나로 오해하게 만들지 않아야 한다.

## 6. 단계별 실행 및 통과 기준

점수는 제작자가 근거 화면과 관찰을 붙이는 점검표이며 객관적인 상용 등급 인증이 아니다. **치명 결함 하나라도 있으면 평균 점수와 무관하게 실패**다. 치명 결함: 공격/예고 범위 불일치, 플레이어 가림, 적탄 식별 불가, UI 정보/조작 유실, 저장/관전 손상, 필수 자산 누락, 지속적인 성능 목표 미달.

실패 기록은 `장면/해상도/시각 → 보이는 문제 → 원인(조형/명도/배치/시간/비용) → 수정 → 같은 장면 재검증 결과`로 남긴다. 두 번 같은 문제가 반복되면 발광·파티클을 더하는 대신 형태·레이어·렌더 방식의 원인을 바꾼다. 기준에 못 미친 그룹이 있으면 다음 그룹의 양산을 중단하고 대표 원형부터 고친다.

장면을 모두 수동 플레이로 기다릴 필요는 없다. 기존 fixture를 확장해 재현하고, 별도로 자연 전투와 시간 흐름을 관찰한다. 캡처의 개수가 화면 품질을 보증하지 않으며 대표 접촉 시트와 실제 크기 이미지 양쪽에서 확인한다.

### 성능 목표와 판단법

- 제품 목표는 대상 데스크톱 Windows/Web에서 안정적인 60fps다. 최소 사양은 아직 검증되지 않았으므로 임의로 저사양 보장을 쓰지 않는다.
- 동일 장치·전원·창·renderer·VSync 조건, 60프레임 준비 뒤 동일 시드/상태를 최소 3회 비교한다. 정적 렌더, 움직이는 모델, 실제 통합 전투를 나누고 CPU/GPU/프레임 대기 시간을 혼동하지 않는다.
- 240적·240탄·300경험치와 실제 가능한 최대 설치물/위험을 포함한 움직이는 장면에서 통합 프레임 p95≤16.7ms, p99≤25ms를 초기 목표로 삼는다. 33.3ms 초과가 반복되면 불합격이다. 목표 변경이 필요하면 실측 근거와 대상 사양을 문서화하고 성능 완료라고 먼저 쓰지 않는다.
- 지금 p95 21.602ms인 정적 fixture를 단순히 유지한 것은 60fps 목표 통과가 아니다. 배경 원·중복 도형·매프레임 배열/StyleBox 생성·텍스처/재질 전환·투명 overdraw 중 실제 병목을 프로파일링하고 줄인다. 예상 원인을 측정된 원인처럼 기록하지 않는다.
- 첫 출격, 새 진화 등장, 대량 획득, 결과/고스트 저장, 관전 seek의 최대 지연을 따로 기록한다. 자산은 사전 로드하고 렌더 중 파일 로드/아틀라스 생성 금지.
- GPU 메모리·RAM·PCK/웹 다운로드 증가를 기준선과 비교한다. 초기 추가 아트 텍스처 메모리 예산은 128MiB 이내, 압축된 신규 다운로드는 약20MiB 이내를 출발점으로 두되, 실제 임포트 결과로 조정한다. 용량을 줄이려고 실루엣이나 판정 표시를 흐리게 만들지 않는다.
- 효과 줄이기는 접근성 설정이다. 이를 켜야만 정상 성능이 나오는 것을 기본 품질의 성능 통과로 처리하지 않는다. 장식 수를 줄이더라도 위험 예고·적탄·충전량은 줄이지 않는다.

## 8. 게임·저장·배포 보호와 완료 선언

보호 대상은 충돌 반경·위성 좌표·공격 범위·경고 시간·피해/수명·난수 순서·수리/붕괴·조작/커서·카메라 변환·미션/업적/랭킹/저장/고스트다. 아트 때문에 선체를 크게 보이게 하더라도 판정은 몰래 바꾸지 않는다. 실제 위험 영역은 채워진 재질과 기준선이 일치하며 바깥 장식은 명백히 비활성 여운으로 읽혀야 한다.

기존 `tools/build.ps1`의 19개 자동 묶음, `tools/verify_uiux.ps1`의 실제 렌더 사례를 마지막에 실행한다. 새 테스트는 자산 ID 전수 연결, 판정/표시 좌표 일치, 정지/관전 시간, 원본 제외/최종 자산 포함, UI 넘침 같은 실제 회귀를 검사한다. 함수 구조나 이미지 파일의 존재만 검사하는 형식적 테스트로 미술 품질을 대신하지 않는다. 원본 RGBA를 완전히 같은 픽셀로 고정하는 테스트는 renderer 차이를 고려하지 못하므로 보조로만 쓴다.

후보는 `build/candidate`, 대응 증거는 `artifacts/candidate`에 둔다. 현재 정상본의 실행 파일·해시·안내·검증 자료를 먼저 보존하고, 후보의 필수 테스트·Windows/Web 내보내기·실제 실행·화면 품질·해시 대응이 모두 확인된 뒤에만 승격한다. 같은 버전명이어도 실행 파일 SHA-256이 바뀌면 새 세대다. 검증 실패는 현재본 교체의 근거가 될 수 없다.

승격 성공 후 이전 배포/대응 증거/임시 백업을 정리해 최신 검증 완료 한 세대만 남긴다. 소스 원형·과거 설계·플레이어 기록/설정은 삭제하지 않는다. 비교용 옛 화면/빌드를 무기한 별도 보관하여 정책을 우회하지 않는다. 정리 차단은 남은 경로와 정확한 이유를 기록한다. 공개 GitHub/Pages 게시가 후속 승인 범위에 없으면 로컬 검증 결과까지만 전달한다.

전체 개편 완료에는 다음이 모두 필요하다.

- 제작 목록의 실제 ID·상태·사용처 전수 전환, 임시 아이콘/다각형 fallback의 의도치 않은 잔존 0.
- 대표 장면과 전체 화면에서 통일된 스타일 확인, 치명 결함 0, 품질표 통과와 실제 움직임 증거.
- 게임 규칙·조작·저장·과거 고스트·해금/페이지/입력의 회귀 없음.
- 대상 Windows/Web의 실제 실행·정량 성능·후보 내보내기·해시/보관 정책 확인.
- `SURVIVAL_V3.md`의 표현 설명과 새 검증 문서를 실제 최종 상태로 갱신. 이전 검증 수치를 복사해 새 결과처럼 쓰지 않음.
- 자동 결과, 제작자의 시각 검토, 실제 장치 성능, 사람의 미적/플레이 수용을 구분해 보고. 사람이 직접 평가하지 않은 항목을 승인 완료로 기재하지 않음.
